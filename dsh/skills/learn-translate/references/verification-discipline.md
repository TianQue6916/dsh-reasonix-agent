## 1. heredoc 折反斜杠：控制字符是隐形炸弹

**现象**（本轮连踩两次）
- `cat >> f.md <<'EOF'` 里写 `\alpha`，落地成 `BEL(0x07) + lpha`；`\beta` → `BS(0x08) + eta`；`\times` → `TAB + imes`；`\frac` → `FF + rac`。
- `pmatrix` 里的行分隔 `\\` 被折成 `\`，矩阵静默塌成一行，**KaTeX 可能不报错**（`\` 在 cases 里恰是换行符）。

**为什么危险**：文件肉眼完全正常（控制字符不显示）、`grep 关键词` 照样命中、KaTeX 只在真渲染时炸，且报错指向 `Unexpected character`，看不出源头。

**判据（交付前必跑，基线全 0）**
```python
b = open(path, 'rb').read()
for name, ch in [('BEL', 7), ('BS', 8), ('TAB', 9), ('VT', 11), ('FF', 12)]:
    assert b.count(bytes([ch])) == 0, (name, b.count(bytes([ch])))
```
（TAB 只在 md 正文里禁；代码块内允许，按需放行。）

**武器**：LaTeX 一律用 write 工具落盘；必须走 shell 时用 `chr(92)` 拼接；写完立刻跑体检，别等 KaTeX。

## 2. 先证伪验证器，再证伪命题

**现象**：SPNE 检验用「**整棵树**的收益」去判某个节点的偏离，一次跑出 **80 个假违例**（还附 43 个零和树违例）。根因不在数学：根没走那条路时，下层节点怎么选都不改变整棵树收益 ⇒ **不可达节点的空威胁被当成合法均衡行为**。

**判据**：出现「量级不对」的违例（几十个，而不是一两个）时，**先怀疑验证器**。数学命题很少错得这么整齐。

**武器**：偏离检验必须锚在被检验节点自己的子树上（`play_from(t, profile, path)`），而不是整棵树。修完 80 → 0。

## 3. KaTeX 校验器自身会假阳性

**现象**：正文里写了 `` `$$` `` 与 `` `\[` ``（行内代码，用来讲格式规范），提取器把它们当公式，报 `Undefined control sequence: \[`。

**判据**：校验器报的错，先看片段是不是**行内代码**或代码块里的示例。

**武器**：提取前剥离所有 ``` 围栏与反引号片段；base64 长行不含 `$`，可安全跳过；对每个报错人工确认一次「是不是我写的公式」。

## 4. hatch 在黑白打印里会消失

**现象**：两张图 v2 用 `hatch='//'` + 浅灰底，缩到 50% 看**完全不可见**，四个格退化成同一块灰 —— 黑白打印直接失去区分度。`read_image` 复核才发现（代码跑通 ≠ 图合格）。

**判据**：黑白可读 = 只用 **线宽 / 边框 / 文字 / 位置** 做区分。hatch 与浅色填充**不得作为唯一区分手段**。

**武器**：砍掉 hatch 与灰底，改用「统一 1.8 线宽 + 关键格 3.6 粗框」。附：matplotlib 的 `hatch` 值本身是含反斜杠的字符串（`'\\\\'`），在 heredoc 里写必塌 —— 与第 1 条同源。

## 5. `[未定位]` 不是免检牌

**现象**：「LLM 自我博弈 / 多智能体训练的承重点」被我标成 `[未定位]`，理由是「材料不够」。用户当场反驳：这类问题人类早就研究过。补查后 20 分钟内拿到五条 A 级来源（CFR 2007 / Deep CFR 2019 / PSRO 2017 / α-rank 2019 / CICERO 2022）+ 一个实现坐标（OpenSpiel 的 league controller）。

**规则**：标 `[未定位]` 前必须完成一次**针对性检索**，并在条目里写清检索词与命中情况；确实检索不到，写「已检索 N 次无一手来源，暂缺」。**禁止用「材料不够」当挡箭牌。**

**与铁律 27 的分工**：27 管「别编场景」，本条管「别懒」。两条合起来才是「不知道就查，查不到就说清楚」。

## 6. 技能摘要可能与 SKILL.md 正文不同步

**现象**：技能注入时给的 v4.5 摘要写着「铁律 34 先攻后守」，而 SKILL.md 第 180 行的现行文本是 **「34 一次讲透，不考他」**（2026-11-15 用户明确反转：禁止出题、留空位、反问「你怎么想」）。按摘要行事会直接违反现行规则。

## 7. 一份真相（防臃肿）

**现象**：附录文档初版 594 行，与主文档重复了三块（审稿清单、卡点、验证链）。用户要求「不要太臃肿，直指核心」。

**规则**：
- 同一份清单**只存一份**；重复的清单会变成第二份真相，之后必然漂移。
- 主文档给**骨架与结论**，附录给**推导**（附录第一行就写明这个定位）。

**效果**：594 → 535 行，且删掉的三块在主文档里本来就有。

## 交付前固定五项体检（可直接抄进 checklist）

1. 控制字符：`\x07 \x08 \x09 \x0b \x0c` 全 0（第 1 条）。

## 8. 落盘前先解析真实路径（同名目录陷阱，2026-11-15）

**现象**：一次交付连续 **4 轮**放错位置。

| 轮次 | 我放到哪 | 为什么错 |
|---|---|---|
| 1 | `课程文件/锚点卡/` | 自建目录；技能 §A2 里写的路径与他实际习惯不符（他还原话「什么锚点卡,不要改我文件夹」） |
| 2 | `待处理文件夹/计算机/` | 按「学科」猜，但目录层级猜错 |
| 3 | `006算法导论/思维文件归档/` | 那是**已归档**区；他原话「这不是我还没做的任务吗,给我放那边干啥」 |
| 4 | `课程文件/待处理文件夹/算法导论/` | **还是错** —— `待处理文件夹` 有两处同名 |
| ✔ | `桌面/待处理文件夹/算法导论/` | 与 `桌面/课程文件/` **平级**的那一个 |

**根因**：`待处理文件夹` 同时存在于 `桌面/` 与 `桌面/课程文件/` 下。我用 `ls`/`grep` 看到其中一个就认定命中，**没有核对完整路径**。

**判据：落盘前必跑三条**

1. `ls -la <目标父目录>` —— 看实际顶层结构，不凭记忆。
2. `readlink -f <目标目录>` —— 符号链接必须解析到真实目标（Linux `~/桌面/待处理文件夹` → `/media/OS/linux-home/桌面-待处理文件夹`；`~/桌面/课程文件` → `/media/OS/linux-home/桌面-课程文件`）。
3. `find <根> -maxdepth 3 -name "<目录名>" 2>/dev/null` —— **枚举所有同名目录**，逐个判断用户说的是哪个（判据通常是「哪个下面已经有他提到的子目录」）。

**用户说「不对」时**：不要只挪一层再问，立刻跑第 3 条列出全部同名候选，再对照他话里的子目录名（如 `数学/` `计算机/`）定位。

**推论（重要）**：技能文档里的路径条目本身可能是错的 —— §A2 曾把「锚点卡」写成规范路径，照做必错。**以 `ls` 的实际输出为准，不以文档为准**；发现文档与实际不符时，改文档（三端同步），不要迁就文档。

**这次的正确判据一句话**：`桌面/待处理文件夹/` = 未完成任务区（与 `桌面/课程文件/` 平级）；`课程文件/<课程>/` = 已归档区。**没做完 → 前者；定稿后才进后者。**

## 9. Windows 上改写含中文的 UTF-8 文件的三种失败（2026-11-15 实测）

在本机（Windows + Git Bash）对 `D:/Desktop/.../backward-induction-*.md` 做原地改写，连续踩三坑：

1. **`sed -i` 替换串里的反斜杠被当转义序列** → `sed: -e expression #1, char 129: Invalid back reference`，**静默不执行**（md5 没变，还以为是成功）。
2. **`perl -i -pe` 直接把文件写坏** —— Perl 按系统 locale（GBK）读写 UTF-8 文件，中文变乱码；之后 `open(..., encoding='utf-8')` 报 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb8 in position 282145`。**这是数据损坏，不是报错即止**；恢复靠 `scp` 从 Linux 侧拉回同 md5 副本。
3. **Python `open(path,'w')` 在该目录报 `PermissionError: [Errno 13]`** —— 同目录 `os.access(W_OK)` 返回 True、shell 的 `>` 与 `>>` 正常、`attrib` 只有 `A`。疑似目录 integrity / 策略层拦截；**不要在这上面耗时间**。

**可靠写法（纯 shell 重定向，已验证）**：

```bash
{ head -n $((N-1)) "$F"; echo 'REPLACEMENT LINE'; tail -n +$((N+1)) "$F"; } > t.$$ && mv -f t.$$ "$F"
```

**校验三连**：`md5sum` 变了、`python -c "open(F,encoding='utf-8').read()"` 通过、`sed -n 'Np'` 内容正确。

**推论**：在 Windows 上改中文名 UTF-8 文件，**优先让 Linux 侧（`ssh`）做**；只用 shell 拼装时立即做 UTF-8 体检；`perl -i` 一律视为不可靠。
