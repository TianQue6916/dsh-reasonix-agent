# 01 · 与 agent 协作的方法论：目标可见、否证纪律、边界铁律

> 这套 harness 的真正瓶颈从来不是模型能力，而是**状态外化**与**否证纪律**：
> agent 不会"记住"任何东西，它只读得到你写下来的东西；它也从不"知道自己错了"，除非测量把它按在墙上。

---

## D 定论

**D1 · 目标必须在每一步被重新注入，而不是"上次说过"。**
长任务里 agent 的目标漂移是默认行为，不是意外。把目标、铁律、进行中事项写进一个每 step 现读的文件（本 harness 是 `.dsh/PLAN.md`，由 `plan-anchor.mjs` 取 head 重注入），漂移才被结构性消除。改文件**不需要重启** —— 它是每 step 现读的。

**D2 · 每条 shell 命令必须有时限（默认 30–60 s，重活 ≤ 120 s）。**
用户原话：「以后每次都给命令设下时限，超过就自己停」。无上限长任务是本 harness 最贵的单点错误：一次 `robocopy` 搬 6.9 GB 桌面跑了 **410 秒**不返回，触发两次「你又卡死了」。

**D3 · 长任务必须后台化 + 进度可见，不能阻塞主循环。**
`job_list` / `job_output` / `job_kill` 这条线存在的原因就是它。同步等待 = 把 agent 的注意力当 CPU 用，而注意力会被浪费。

**D4 · 多方案先给选项，决策权不外借。**
出现多个可行路径时：给选项 → 对比（成本 / 风险 / 可逆性）→ 给推荐 → 由人拍板。不要自己选定一个就落地。理由不是礼貌，是**可逆性**：人掌握 agent 看不到的代价（时间、精力、外部约束）。

**D5 · 诊断顺序固定：现象量化 → 假说 → 阳性对照 → 否证入档。**
跳过任何一步，结论都会在下一次复发时被推翻。「已排除」清单和「结论」同等重要（见 10 篇）。

**D6 · 改配置前先做零副作用校验，改完用"新 session"验。**
`--dump-config` 类命令是零副作用的合成结果校验；而 patch 类改动要「开新 session 即生效」，preset/bundle 类改动必须重启进程。**用旧进程验证需要重启的改动 = 假阴性制造机。**

**D7 · 事故的产出是「判据」，不是「故事」。**
判据 = 未来 30 秒内能判定"是不是同一个问题"的可观测信号。没有判据的复盘等于没复盘。

## M 机制

**M1 · 为什么状态必须外化：LLM 的"记忆"是上下文窗口，而窗口是会被压缩、截断、被新内容挤走的有损缓存。**
外化的成本（写 20 行 md）远低于内化的成本（每步多带 3 k token，且随时可能被 compaction 丢掉）。这是同一件事的两种存法：**文件 = 可寻址的持久层，上下文 = 易失的寄存器**。

**M2 · 为什么"限时"是铁律而不是建议：单条命令的期望耗时分布是重尾的（heavy-tailed）。**
正常命令 100 ms–2 s，异常命令可能几分钟到无限。agent 无法在发起前区分两者，所以只能用**上界**约束；超时不是失败，是"信息不足，需要拆片或后台化"。

**M3 · 为什么"先给选项"能提高总吞吐：agent 的搜索空间比人大，人的代价函数比 agent 准。**
把搜索交给 agent（枚举 + 对比），把选择交给人（一次决策），比让 agent 猜一个代价函数要稳定得多。

**M4 · 为什么否证必须入档：agent 每次会话都是"失忆的新人"，而人也会忘。**
同一个假说被反复试验，是长会话里最贵的浪费形式 —— 它看起来像在工作，实际在原地。

**M5 · 为什么"参数化测量"比"感觉"可靠：本 harness 的多数误判来自探针失效，而不是现象消失。**
没有阳性对照，你无法区分"没有这个现象"与"我的检测根本测不到"。

## J 判据

**agent 正在漂移的信号（命中 2 条以上就该停下来重注入目标）：**

| 信号 | 具体表现 |
|---|---|
| 重复试错 | 连续两轮尝试同一个已被否证的假说 |
| 不看证据 | 不读 traceback / 日志就改代码 |
| 静默长跑 | 单条命令 > 60 s 无输出（应已超时） |
| 模糊断言 | 输出里出现"应该/大概/估计是这样"，且没有对应观测 |
| 越权决策 | 未经人拍板就落地了多方案中的某一个 |
| 忘记范围 | 开始修改与当前目标无关的文件 |

**改动是否真的生效（三问）：**

1. 这个改动属于哪个重载层？（patch/profile → 新 session；preset/bundle → 重启进程）
2. 我是在**验证生效**，还是在**验证我想让它做的事**？两者需要不同观测。
3. 有没有**对照**？（同一观测在改动前后各测一次，或在新旧进程上各测一次）

**诊断是否合格（四问）：**

1. 现象有数量吗？（"白纸图标"不如"`sat=0.6`、`bright_px=34.0%`"）
2. 有阳性对照吗？（已知正常的样本也要跑同一探针）
3. 排除清单写了吗？每条的否证证据是什么？
4. 结论能预测一个**未被观测过**的结果吗？不能预测的结论只是描述。

## X 反例

**X1 · 无时限命令。** `robocopy` 搬 6.9 GB / 410 s，卡死主循环、两次被批评。**任何**可能超过 60 s 的操作都要么拆片、要么后台化、要么先估规模。

**X2 · 用旧进程验证需要重启的改动。** 在 web 旧进程（pid 28480）上验证 thinking 相关 patch，结论是"没生效"；换成新 session / 重启后才是真值。判据：进程启动时间戳 vs 改动时间戳。

**X3 · PowerShell 5.1 读无 BOM 的 UTF-8 `.ps1` 会按 GBK 解码。**
⇒ 脚本里的中文字面量永远匹配不上真实 Unicode 标题 ⇒ 早期"对话框探针"的 `dialog_count=0` **全部是假阴性**。改用窗口类名（`#32770`）或 Python + `ctypes` 才是对的。

**X4 · 单点测量下结论。** 用单个文件的 `file=3` 值判断、用 `ExtractAssociatedIcon` 判断 —— 都被后续多点测量推翻。

**X5 · 忽略文件被占用。** 读 explorer 占用的文件必须用 `FileShare.ReadWrite`；`Open(...,'ReadWrite','None')` 必然失败，会被误读成"文件损坏"。

**X6 · 把惰性分配当失败。** iconcache 的 24 B 快照**不是**写失败，那是惰性分配，随后 32/48/256 尺寸都涨到 1 MB。

**X7 · 提权 ≠ 解除限制。** `sandbox: danger-full-access` 在 Windows 上不改变 integrity level；进程仍是 Low IL，D 盘照旧只读（详见 09 篇）。**配置写对了不等于行为变了**。

**X8 · 在没有阳性对照的情况下宣布"已修复"。** 没有对照的探针，只能证明探针没报错。

**X9 · 把"我猜的原因"写进 PLAN 而不标注状态。**
PLAN 里必须区分 `已确证 / 最强嫌疑 / 已否证`，否则下一次读它的人（包括未来的自己）会把嫌疑当结论。

## R 复现

**每次实质任务的开场（30 秒）：**

```bash
timeout 20 sed -n '1,40p' ~/.dsh/PLAN.md          # 目标 + 铁律
timeout 20 grep -n "^## \|^### " ~/.dsh/PLAN.md | tail -40   # 当前进行中
```

**每条命令的模板：**

```bash
timeout 40 <cmd>            # 默认 30–60
timeout 120 <heavy-cmd>     # 重活上限，且必须可拆
```

**改动生效验证（两段式）：**

```bash
# ① 零副作用合成校验
timeout 60 dsh --profile <name> --dump-config | head -50
# ② 新 session 实测（不要用旧进程）
```

**诊断记录的最小模板（可直接追加到 PLAN.md）：**

```md
### <现象一句话>（<时间>）
- 现象（带数量）：
- 探针 / 命令：
- 阳性对照：
- 已否证（含证据）：
- 当前最强嫌疑：
- 判据（下次 30 秒内怎么认出它）：
```
