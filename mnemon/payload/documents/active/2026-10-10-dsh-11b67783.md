# 主力机写入量第三轮排查（2026-10-10）

用户反馈「我啥都没干，这两天就玩了会游戏」却看到磁盘写入统计异常，要求揪出元凶，并特意叮嘱「注意社区经验」。这是 10-05 两轮写入归因（863dee8c、63c87fcc）之后的第三轮。

## 1. 口径纠错（本轮第一产出）

- 单窗口 delta 数字（34 → 152 GB/天）**是噪声，不是翻两番**。
- 按累计口径重算：`Data Units Written` 4 天 +335 GB / 3.98 天 = **84 GB/天**，历史均值 ~57 GB/天 ⇒ 只有 **~1.6 倍**。
- `smart-history.csv`（/d/CrystalDiskInfo/_history/smart-history.csv）按行 delta_written_GB / delta_days 得到 GB_per_day：10-07 = 34.43、10-08 = 67.8、10-09 = 91.51、10-10 = 151.78。**只有按累计 delta 除以真实天数才可比**，逐次差值直接比会得出翻倍假象。
- 未对账项：`Data Units Written`（raw `written_bytes`）是 **NAND 侧、含 WAF**，与 `Host Writes`、与文件系统新增字节都不是一回事，**不能跨口径相减**。
- 与 863dee8c 的采样窗口假象同源（60s 窗口给出 45× 高估）。

## 2. 已排除项（带量）

- **dsh 自身（自指偏差，结论：排除）**：20s 采样把 `deepseek harness` 记为 8.47 MB/s，但那 20 秒里正在跑自己的 `find`/`Get-Counter`，dsh 会记录每一步 tool call。实测 `~/.dsh` = 1.8G、`~/.dsh-lab` = 461M，4 天内两棵树共改 **0.23 GB / 405 个文件**；最大单文件 `~/.dsh-lab/tmp/app.patched.asar` 123 MB（10-07）；`~/.dsh/logs/host-stdio.log` 5 秒只长 106 字节 ⇒ **~1.8 MB/天**。
- CrashDumps：`nahimicNotifSys.exe` 每天崩一次，27.8 MB/个，4 天合计 ~110 MB。
- `D3DSCache` 3.7M；`NVIDIA\DXCache` 1.7G 但 4 天未改动；`WUDownloadCache` 8K；`DeliveryOptimization` 983M；`GameViewer` 114M。
- Event ID 55 = CPU 电源、Event ID 10001 = DCOM 权限，均为噪音。
- **C 盘与 D 盘都扫不到 >30 MB 的新文件** ⇒ 写入形态是覆盖或写后即删，不是新增内容。

## 3. 未解释的反常：随机命名目录指纹（本轮新线索，安全相关）

D: 根下出现成对目录，内部文件创建时间完全相同，两份内容逐字节同尺寸：

```
/d/ZDATA485      772K   mtime 2026-10-10 12:31
/d/ CACHE990     772K   ← 目录名有前导空格
  RQ5egT4i.mdb 174986 | Jp2CF7taEo.xls 101038 | N2ld5Yk610N.pem 90109
  sAdf6PvjWFAcZ0tg.xlsx 85458 | wxPEdGD.txt 83436 | D8b4O.jpg 77825
  ymRI2miPv5OZB3Tbp.rtf 68880 | 0Mvz9Qqjx.docx 55362
```

后续同类：`/d/ZFILE745`、`/d/ DOCUMENT28`（2026-10-10 13:15）。

特征 = 随机目录名 + 随机文件名 + 混合扩展名 + 两份完全相同内容，全部同一时刻创建。典型指纹是**程序在扫描 / 测试磁盘可写性**（勒索软件探测，或某些「优化/激活」类工具）。
**量太小，不足以解释 335 GB；但在安全上必须标记，并按此方向继续追溯创建者。**

## 4. 方法学陷阱与仍待查项

- `find -newermt` 在 MSYS 下对 `/d/CrystalDiskInfo/_history`（该文件确实在 10-10 12:56 被写）返回空，`find -mtime -4` 同样返回空 ⇒ **该 find 用法在此环境不可信**，不能据此下「没有新文件」的结论。（证据不足以判定是 find 语义还是命令写法问题，需用正确写法复验。）
- VSS shadow storage / shadow copies 查询未拿到有效输出（cmd 未真正执行），仍待查。
- 静态存量（非 4 天内增长）：`/d/代码缓存` 3.1G；`/d/50-游戏` 276G（其中 Games 17G、MCLDownload 9.5G、FeverApps 5.1G）。
- `/tmp` 是 MSYS 路径，PowerShell 不认，须换 Windows 路径。

## 5. 对社区 / AI 建议的事实核查（用户点名「注意社区经验」）

- 推荐方向（Procmon / Sysmon 做实时 I/O 监控）方法正确，但**只能抓未来**，且 Procmon 日志量极大（几分钟数 GB），在写受限的机器上是负优化；「先算清账再决定要不要装工具」。
- **硬伤一**：`C2ME` = Concurrent Chunk Management Engine，做 chunk 加载/生成的并发化，目标是 CPU 与吞吐，**不是磁盘 I/O 优化 mod**，当 HDD 优化装是方向反的。
- **硬伤二**：所谓 `HDD Mode` mod **查不到存在**。MC 社区真正用于降 I/O / 降内存的是 `FerriteCore`、`ModernFix`、`MemoryLeakFix`、`Lithium`、`Sodium`。
- MC 物理机制核查：区块保存是**周期性小写**（默认 autosave 约 45 秒一次、每次 MB 级），量级撑死几百 MB/小时，撑不起 84 GB/天。但其方向不全错——shaderpack 编译缓存、`logs/latest.log` 高频 flush、crash loop 反复重启是被低估的写入源，**需实测不能靠猜**。

## 6. 结论与待办

- 结论：现有数字落在 ~1.6 倍区间，dsh 与常见缓存均已排除，**元凶未定**；优先顺「随机命名目录 / 磁盘可写性探测」这条安全线索走，同时一律用累计口径而非单窗口 delta 复核。
- 待办：① 查 VSS shadow storage；② 用可靠写法重做一次「4 天内改动」全盘扫描（验证 find 用法）；③ 监控 `ZDATA485` 类目录是否再出现并追溯创建者。
