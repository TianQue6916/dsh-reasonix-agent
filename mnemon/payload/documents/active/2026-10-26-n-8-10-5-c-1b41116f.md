# 实现语言分层契约的本机实测校准（2026-10-26）

配套/前序文档：`efcb68aa-835e-4e42-8de2-26b6c2e154b3`（《实现语言分层契约（方案 A）…》）记录的是**事前估计**版本（`N* ≈ 6×10^5`、`c_py ≈ 60 ns`、benchmark 未跑、WDAC 待复核）。本文是同一策略的**实测校准 + 两处结论翻转**，会与那份文档的数字冲突，冲突时以本文为准。

环境：Windows，非管理员，Python 3.13.9 / NumPy 2.3.5 / MinGW-W64 UCRT gcc 15.2.0（无 rustc、无 MSVC）、PowerShell 7 + 5.1 并存。所有脚本与产物在 `.dsh/scratch/lang-bench-20261026/`（`hello.c`、`sumloop.c`、`countneedle.c`、`b_startup.py`、`b_core1.py`、`b_core2.py`、`b_core3.py`、`data/log100.txt`），可复跑。

## 1. 启动开销（中位数，warm×3 后测 21 次，丢前 3 次 warmup）

| target | median | min | p90 |
|---|---|---|---|
| `python -c pass` | 21.40 ms | 20.36 | 25.53 |
| `python -c "import json,re,pathlib"` | 38.67 ms | 32.68 | 41.13 |
| `hello.exe`（`gcc -O2 -static`） | 7.79 ms | 6.51 | 8.44 |
| `cmd /c exit` | 15.60 ms | 14.73 | 17.60 |
| `pwsh -NoProfile -Command exit` | 200.76 ms | 185.65 | 207.13 |

⇒ pwsh 启动 = Python 的 **9.4×** = gcc exe 的 **26×**。用户长期抱怨的「命令太慢」，成本主体是**每次 cold-spawn pwsh 的 200 ms**，与语言/字节码无关。这把「① 合并 / 减少工具调用」的优先级从直觉升级为可量化收益：一次排查 spawn 5–10 次 pwsh ≈ 1–2 s 纯启动税。

## 2. 内层循环成本与交叉点（`s = Σ i`）

| N | py for 总 | py ns/iter | C 总（含 5.92 ms 启动） | numpy 总 | py/C |
|---|---|---|---|---|---|
| 10^4 | 0.17 ms | 17.1 | 5.96 ms | 0.003 ms | 0.0（Python 快 35×） |
| 10^5 | 1.83 | 18.3 | 5.48 | 0.021 | 0.3 |
| 10^6 | 19.73 | 19.7 | 7.64 | 0.211 | 2.6 |
| 10^7 | 198.44 | 19.8 | 8.89 | 4.857 | 22.3 |

- 实测 `c_py = 19.8 ns/iter`，比教科书经验值 60 ns **快 3 倍**（CPython 3.13 的 PEP 659 specializing adaptive interpreter 对 `for i in range(N): s += i` 做了专精化）。**以后估算不要套 60 ns。**
- 重算交叉点：`N* = (21.40 − 5.92) ms / (19.8 − 0.3) ns ≈ 8×10^5`，与原估计 6×10^5 同量级 ⇒ 判据成立、常数更新。
- N=10^4 时 Python 快 35 倍（C 全在付启动）；N=10^7 时 **NumPy 4.86 ms < 自写 C 再 spawn 8.89 ms** ⇒ 消灭解释器循环优于换语言。

## 3. 102 MB 日志数 `ERROR`（1.4 M 行 / 14000 命中 / 每行 71 B）

| 实现 | median ms | MB/s | 备注 |
|---|---|---|---|
| `findstr /M`（仅判存在） | 9.1 | 11220 | 最快，但**不给计数** |
| `python data.count(b"ERROR")`（预读内存） | 12.07 | 8458 | 拿计数最优 |
| `python f.read()`（纯 I/O） | 35.42 | 2883 | **I/O 硬底，换语言无用** |
| `C countneedle.exe`（memchr，端到端） | 53.08 | 1924 | 启动 5.9 + fread 35.4 吃掉全部收益 |
| `python mmap + count` | 67.05 | 1523 | |
| `findstr /C`（输出 14000 行） | 135.2 | 755 | 格式化/输出主导 |
| `python for line in f` 逐行 | 324.5 | 315 | 1.4 M 次解释器迭代 |
| `pwsh Select-String` | 2754 | 37 | **最慢，大文件禁用** |

三条结论：

1. **自写 C 在文本处理上是负收益**：bytes.count(12 ms) 比我手写 memchr exe(53 ms) 快 4.4×。拆解 `53 = 启动 5.9 + fread 35.4 + memchr ~11`，而 `bytes.count` 的内核**本身就是 C 写的 two-way 算法**。⇒ 用户诉求「绝大多数处理用 C 写」在文本场景买不到任何东西，只会换掉一个已经用 C 实现好的内核。
2. **324 ms ↔ 12 ms 是写法差异不是语言差异**：同一个 Python，逐行 for 是 324 ms、`data.count()` 是 12 ms，**27 倍**。这是「优先级②消灭 O(N) 解释器循环」的实测证据，改动成本≈0。
3. **PowerShell cmdlet 不是「快」的代名词**：`Select-String` 仅 37 MB/s，比 `bytes.count` 慢 228×（逐行构造 `MatchInfo` 对象）。**rev1 文档里「系统工具优先」需收窄为「原生的、批量语义的系统工具优先（findstr /M、robocopy /MT），不是 cmdlet 优先」**。另外 `where rg` 为空 —— 本机**没有 ripgrep**，rev1 把 rg 列入「优先」是错的。

## 4. WDAC 复核：结论翻转（native 路线可行）

| 项 | 值 | 含义 |
|---|---|---|
| `CodeIntegrityPolicyEnforcementStatus` | 2 | Enforced，但属 HVCI 内核态 CI（驱动签名），不拦用户态 exe |
| `VerifiedAndReputablePolicyState` | 0 | Smart App Control 关闭 |
| `SkuPolicyRequired` / `EmodePolicyRequired` | 0 / 0 | 无 SKU 强制策略 |
| CodeIntegrity 事件日志 | 无 3077 | 无「拦截未签名程序」记录 |
| 实测 | `hello.exe` / `sumloop.exe` / `countneedle.exe` 全部 exit=0、输出正确 | **未签名 exe 可执行** |

⇒ rev1 标记的「WDAC 是全 C 路线最大不确定性」可以划掉：**native 走进程边界在本机技术上完全可行**，选型不因此受限。

**顺带修正一条旧归因**：MEMORY 里「PowerShell 5.1 跑 `.ps1` 报 not digitally signed」被归因于 WDAC，很可能是错的。实测执行策略 5.1：CurrentUser `RemoteSigned` / LocalMachine `Unrestricted`；pwsh 7：LocalMachine `RemoteSigned`。更可能是 **MOTW（Zone.Identifier）+ RemoteSigned**，`Unblock-File` 可解 —— 此条仍是**推断，未用 `Get-Item -Stream Zone.Identifier` 直接验证**。

## 6. 踩坑记录

- **Git Bash 里 `cmd //c 'findstr /C:"[ERROR]" ...'` 返回 `exit=1` 是假阴性**：引号与方括号被转义层吃掉，害人误判 findstr 没命中。改用 `subprocess.run(["findstr", ...])` 列表式调用才拿到正确的 14000。⇒ 在 Windows 上测外部命令不要经过 bash 转义层。
- `findstr` 实测变体：`/C` 135.2 ms、`/L /C` 131.7 ms、`/M /C`（仅文件名）9.1 ms、`/C /N` 132.3 ms。
