# dsh「已达到输出 token 上限」通知假警报：取证与抑制补丁（2026-10-03）

## 现象与问题来源

用户（m02056）问：为什么**别的对话**会弹出「已达到输出 token 上限 / 回答被截断…发送『继续』」。
排查确认：既不是用户配置问题，也不是把输出预算真烧完，而是**上游把流中断后仍回了 `finish_reason:"length"`** 造成的假警报。

## 触发链（逐字引用行号）

- notice 匹配条件在 core UI bundle `@deepseek-ai/dsh-client-ui-chat/lib/client.js`：
  - `:9920` `if (match.event.type !== "turn/end" || match.event.data.reason.kind !== "max-tokens") return void 0;`
  - `:9932` `if (event.type === "turn/end" && event.data.reason.kind === "max-tokens") return {`（notice 定义 `kind: "turn-max-tokens"`，target `chat`）
  - 文案 `:5527 "message.maxTokens"` / `:5528 "message.maxTokens.hint"`（「发送继续」属同一节点）
  - 对照：`message.turnProcess.took`（`:5423`）是**正常** turn 完成标记，未改动。
- `max-tokens` 的来源：provider 返回 `stopReason:"length"` → `dsh-llm-pi-ai/lib/index.js:1422` `case "length": return { kind: "max-tokens" }`。
- 事件数据位置：`turn` 在 `data.turn`、reason 在 `data.reason`；只有 `assistant/attempt.data.stream` 才有原始 finish/usage。

## 判定为假警报的证据

会话 `session-b65a9a67-80a1-403c-b899-45b0ac351801`（用户另一个会话，非本会话、非 mnemon 后台 review）：

| turn | 时间 | 时长 | 结束 reason |
|---|---|---|---|
| 13 | 13:15:08 → 13:17:25 | ≈2m16s | `{"kind":"max-tokens"}` |
| 15 | 13:36:43 → 13:39:46 | ≈3m3s | `{"kind":"max-tokens"}` |

- 该 turn 的 `request/header.data.header.config` = `{provider:"commandcode-goat", model:"deepseek/deepseek-v4.1-flash", reasoningEffort:"high", maxTokens:262144}`、`adapterDefaults:{maxTokens:true}` ⇒ **预算 262144 确实下发**（与 mnemon review 的 4096 截断是两码事，那条修复独立有效）；实际最后一步 completion 仅 **2899 tokens**。
- 同 turn 内并存：`assistant/attempt` 流末块 `{"kind":"error","failure":{"message":"upstream stream ended before a completion event; this turn may be incomplete","code":"TRANSPORT"}}`，同秒 `llm/retry`（retry 1/8）→ `llm/retry-started`；gateway 侧 `STREAM-ERR id=154 key=163 upstream aborted`。
- gateway 侧 10-03 全天 `completion_tokens` 峰值仅 14828（次 13150 / 12944 / 12318 / 11394 / 10150），`prompt_tokens` 峰值 186918；gateway **不改写 `max_tokens`**（`grep max_tokens gateway.mjs` 零命中）、**不合成 `finish_reason`**，只在 loop-guard abort 时补一个 `data: [DONE]`。
- `/v1/models`（gateway `:1498`）61 个模型**无任何 `max_output_tokens` 字段**，6 个 deepseek 条目 `context_length` 均为 1000000 ⇒ 本机无法确认上游是否有更小的隐式输出上限。

## 修复：让 notice 节点不再生成（不改文案）

做法：只把 UI 判定用的两处**带引号字面量**做等长 ASCII 替换 `"max-tokens"` → `"max-tokenz"`（12 B → 12 B）。
- **harness 内部语义一律未动**：`finish.kind === "max-tokens"`、session 事件 `turn/end` reason、`dsh-llm` 在 max-tokens 时丢弃 tool-call 块的行为全部原样 ⇒ 截断事实仍完整落盘，诊断能力零损失。
- **anchor 必须带前缀**：必须是 `reason.kind !== "max-tokens") return void 0;` 与 `reason.kind === "max-tokens") return {` 两串；asar 内 `"max-tokens"` 共 **29 处**，其中 harness 内部的 `finish.kind === "max-tokens"`（`app.asar` 内偏移 14468205）必须保留，盲替换会破坏语义。
- 两个 target 及偏移（等长替换 ⇒ 文件长度与 asar header 偏移无需重算）：
  - npm-js `…\@deepseek-ai\dsh\node_modules\@deepseek-ai\dsh-client-ui-chat\lib\client.js`：464175 / 464564（565455 B）
  - desktop `…\Programs\DeepSeek Harness\resources\app.asar`：19677465 / 19677854（121348951 B）
- `~/.dsh/profiles/*/node_modules` 下**没有** `dsh-client-ui-chat` 副本（find 无结果）⇒ 只需打上面两份。
- 工具与文档：`~/.dsh/storages/tools/patch-maxtokens-notice.py`（`--check / --apply / --verify / --restore`，state 文件保证幂等，重复 `--apply` 被拒并提示先 `--restore`）；说明 `~/.dsh/patches/README-maxtokens-notice.md`；备份命名 `client.js.bak-20261003-134632-pre-maxtokens-notice`（asar 按偏移 + 原字节备份恢复）。
- **生效条件**：client bundle 在进程启动时加载、不吃 HMR ⇒ 需重启 App（web 侧重启 web 进程）。

## 本机修不了的边界

「上游中途断流却标 length」发生在 provider 侧；本机无法读取其输出上限。dsh 侧现有自动 retry（本次 1/8 已恢复流），加上本次隐藏误导性通知。
