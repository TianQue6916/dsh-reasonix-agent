# fluxscope 空间站化与真实网络对端（2026-11-01）

承接 [fluxscope v10–v11](9996766a-350e-47fe-b820-c142820d52f8)（WebGL2 环形拓扑）与 [extract 增量缓存 / tunnel 分环](06b2165d-4459-4fc5-808b-8e5e84b69d37)。三个 commit：`abf77c6`（舱窗 shader、8 环隧道、历史热度、结构骨架）、`56ce165`（舱壁立体化 + 数据流聚焦到具体文件）、`2d3d3de`（真实网络对端进场景；修 `loadSys` 从不重拉）。

## 1. 为什么「不够震撼」不是配色问题

用户连续三次反馈「不够震撼」。对照三个社区案例（Obsidian galaxy dashboard、dsh-graph-view、3d-force-graph 科幻看板）后定位到**三个结构性错误**，配色只是表症：

| 病因 | 后果 |
|---|---|
| 相机 pitch 0.40，接近正俯视 | 六个环压成一个平面同心圆，隧道感为零 |
| 亮度只编码 recency | 1584 个 agent 里约 1500 是 cold，画面大部分是暗的 |
| 格子是平面色块 | 无厚度、无结构件，读起来是图表不是物体 |

修法按影响排序。

### 1.1 舱窗 shader（一格换整套视觉语法）

VS 把 `aCorner` 传给 FS，FS 把每个格子切成 2×3 的窗格阵列，带缝隙和亮边。一格不再是色块，而是「金属外壳上的一排亮窗」。这是空间站观感的整套语法，成本只有一个 instanced draw 的 FS 改动。

### 1.2 三态亮度：大多数格子应是「休眠钢」

```
休眠钢（>1h）   0.34 + 0.26 * h   冷灰，亮度只由历史工作量决定
通电（<1h）      0.72 / 0.78 / 0.86   冷白
全开（<3min）    1.00 / 0.84 / 0.58   暖白
```

中间做过一版错解：让 history heat 直接暖化，整个画面变成暖白灯箱。**空间站是冷钢 + 少数亮窗，不是发光体。**

副作用收益：历史此前一直在库里但没有任何视觉通道；亮度编码历史工作量后「一开机就是满的」，不需要现场重新积累数据。

### 1.3 结构骨架

中心轴 + 每环一个环箍 + 16 条径向桁架。流浪地球质感的来源不是配色，而是**每个面都有东西撑着**。

## 2. 立体感：同一 draw 里的 iMode

外圈显得平，是因为每圈只画了一个上表面。加一个 `iMode` 位：同一个 instanced draw 中 mode 0 画甲板、mode 1 画挂在下面的舱壁（竖向肋条、无窗、更暗）。quads 216 → 528，仍是**一次** `drawArraysInstanced`。

## 3. 数据流聚焦到具体文件

原实现：993 条边一次全画。每条边本是「这个文件被那个会话读写」的具体事实，但画出来两端都认不出是谁 —— 用户的原话是「不要笼统的条子」。

改法：
- **无焦点**：只画最近 10 分钟（原为 2 小时 + 24 条兜底）。
- **有焦点**（hover / 点击文件格或会话格）：只画与它相连的边，端点加三角箭头；悬停文件格会列出哪几个会话碰过它、各几次。

前提改动：link 记录新增 `fp`（文件路径）与 `aid`（会话 id）。此前**只存了角度**，因此无法按文件过滤 —— 这是「加过滤」先要补的数据结构欠账。

## 4. 真实网络对端进场景（`2d3d3de`）

### 4.1 两个被压扁的真相

`sysprobe.ps1` 早就在采 `netR/netT/diskR/diskW`，但前端 `loadSys()` 把它们塞进 `SYSD` 之后没有任何消费者；并且 `loadSys()` **只在失败时重试**，成功之后再也不会重新拉取 —— 与 `loadTopology()` 是同一类 bug。用户质疑「怎么可能只有这么点」时，底层实测是 15874 次调用 / 1594 个 agent / 113 MB/s 磁盘读：不是数据少，是显示层把它们压成了一个数字。

### 4.2 采集与渲染

`sysprobe.ps1` 每 2s 枚举 `Get-NetTCPConnection` 的 Established 对端，带 owning process（PID → 进程名做缓存），过滤 loopback / RFC1918 / CGNAT。实测稳定 20–24 条。每条 = 站外一个停靠模块 + 一条带流动粒子的链路，粒子数 = 该 endpoint 的连接数，全部可对回 `Get-NetTCPConnection` 的一行。

`server.mjs` 侧 `startSys()` 以子进程跑 `sysprobe.ps1`，逐行解析 stdout 的 JSON，写 `SYS`/`sysHist`（上限 180 条）并 `broadcast('sys', SYS)`；进程退出后 4s 重启。前端 `loadSys()` 读 `/sys` 的 `{sys, hist}`，映射 diskR/diskW/netR/netT 到 `SYSD`。

### 4.3 自检口径

`__gldbg` 里 `peers`/`peerDrawn` 应相等且等于实测对端数（实测 24/24）；`drawn`/`recent`/`linksTot`/`quads`/`nanN`/`maxAbs` 用于判断画面是否真的在动、有没有 NaN 污染。

## 5. 教训清单

1. 新增数据先确认**有没有消费者**：`SYSD` 里躺着四个吞吐量字段而场景不用，是最难发现的「假死」。
2. 轮询函数的失败重试分支很容易掩盖「成功后再也不拉」的 bug —— `loadSys`、`loadTopology` 都中过。
3. 过滤类需求往往先要补数据结构（link 之前只存角度，无法按文件过滤）。
4. 装饰层有上限：加完骨架/扫描/舱壁后就该转向**数据密度**（吞吐量做成脐带粒子密度、记忆↔会话边受 192 格容量限制只 56 条），继续加装饰会开始压数据。

## 6. 当前遗留

- `diskR/diskW/netR/netT` 仍未进入场景（数据在 `SYSD` 可用），可做成 4 条脐带的粒子密度 / 流速。
- 记忆 ↔ 会话边只 56 条，源于 192 格容量上限，多数 doc 的 `sessionIds` 指向没进环的老会话。
