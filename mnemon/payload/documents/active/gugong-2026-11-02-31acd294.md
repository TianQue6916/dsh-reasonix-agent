# gugong 交付轮：攒当反解、铺作层次与瓦面叠压

承接 [首版总览](documents/active/gugong-2026-11-01-4f6ab4e1.md)、[一手文献驱动的尺度校准](documents/active/gugong-2026-11-01-73123185.md)、[AABB 布局审计](documents/active/gugong-aabb-2026-11-01-4f403d42.md)。本文只记这三份未覆盖的两处构造改动与最终交付口径。

## 1. 斗拱攒当：从明间宽反解，而不是调系数

commit `d689c06`「斗拱按柱网布」。规则：

```
攒当 = 明间宽 / (明间攒数 + 1)
```

太和殿明间宽 8.45 m、明间 9 攒 ⇒ 攒当 0.939 m ⇒ 斗口 85 mm；进深方向攒当 1.246 m。此前 `_dougong_band` 用固定 `step = 1.55` 均布，导致攒当与开间脱钩，斗拱与柱缝对不上。改后斗拱落点由柱网派生，与「明间开间 = 8.43」这类可互验的一手关系自洽。

## 2. 铺作层「不外扩」才读得出斗拱

`_dougong_band` 原来是一个向外扩 0.55 m 的青色大盒（`MAT_SOFFIT`），把每一攒斗拱整个包在里面——近景看到的是一整片青平面，斗拱只是平面上几个凸点。改法：

- 铺作层贴墙、深色、**不外扩**，斗拱才真正凸在墙外，檐下有「一攒攒」的层次；
- 补檐椽（一排细方杆，间距 ~0.42 m，向外挑出）与连檐（挑檐枋外缘细横条，收住椽头）。缺这两样时檐椽读作「从青面里斜着冒出来的刺」，构造成立不了；
- 额枋 / 铺作层 / 挑檐枋三段拉出深浅层次。

教训：近景细节的失败常不是「模型不够密」，而是**前景体块把该凸出的构件吞掉了**——先减包络，再加构件。

## 3. 板瓦「压六露四」

commit `7746d89`：瓦垄按坡向分级（上/中/下段），段尾加竖直叠压面，实现压六露四的错叠观感，而不是一片均匀半圆瓦垄。瓦件则例尺寸与半圆截面见 [AABB 审计文档](documents/active/gugong-aabb-2026-11-01-4f403d42.md)。

## 4. 交付物规格

- 模型：`out/forbidden_city.obj`，203 MB，517.2 万 verts / 172.4 万 tris，生成 31.1 s，可直接进 Blender / MeshLab。
- 6 张渲染图（`out/`）：`01_axis_aerial` 2400×1500 中轴俯视、`02_santai` 2200×1450 三台与前三殿、`03_taihedian` 2000×1350 太和殿东南、`04_yangong` 1800×1150 檐下斗拱近景、`05_corner` 1600×1100 城墙西北角楼带阴影、`06_yuhuayuan` 1700×1150 御花园。
- 入口：`shoot_final.py`（一次跑通 6 图 + OBJ）、`build_scene.py`（总平面）、`core/building.py`（单体：斗拱/屋面/台基）、`data/site.py`、`data/wa.py`、`audit_layout.py`（碰撞审计，114 对全为设计使然的 T 形墙接头）、`README.md`（尺寸来源与偏差表）。

## 5. 判据状态与下一步

8 项实测判据全部落在 2% 内：望柱 1454 vs 1458（−0.3%）、太和殿通高 35.68 vs 35.05（+1.8%）、明间面阔 8.45 vs 8.43（+0.2%）、明间进深 11.21 vs 11.15（+0.5%）、保和殿 23.54 vs 23.686（−0.6%）、午门 37.59 vs 37.95（−0.9%）、太和门 24.00 vs 23.8（+0.8%）、神武门 31.50 vs 31（+1.6%）。

方法论：前十几轮是「调系数拟合数字」；这一轮改为**先找能互相验算的一手记载，再让几何跟着走**——判断依据是「12.64 / 1.5 = 8.43 = 明间开间」这类能自己咬合的关系，找到一条，周围尺寸自动收敛。
