# Linux 终端 dsh 启动失败的第二根因：PATH 命中了另一套安装

关联文档：`cda4736b-c1bd-438d-86e2-bc0d1ca68c3b`（第一根因：dsh-tunnel 抢 3080，已修到 3081；含 dsh-linux-fix.sh 两个解析 bug）。本文记录接续排查出的第二根因与最终端口分工，两者是叠加关系，只修一个仍会失败。

## 1. 现象与关键线索

修好端口后用户终端仍报错，且 `AggregateError.errors` 里其实有两条独立错误：

1. `webserver (required): listen EADDRINUSE 127.0.0.1:3080`（已由第一轮修复）
2. `failed to import preset-anchored-standard (@deepseek-ai/dsh-agent-preset): Cannot find package ... imported from /home/tianque/.dsh/profiles/web/`

**判定性线索是报错栈中的绝对路径**：`file:///home/tianque/.local/node22/lib/node_modules/@deepseek-ai/dsh/...`，而维护者 SSH 侧跑的是 `.local/lib/node_modules/...`。同一台机器上存在三套 node 环境、两套 dsh。

## 2. 三套环境对照（Linux，主机 TianQue）

| 位置 | node | dsh | 含 `dsh-agent-preset` |
|---|---|---|---|
| `~/.local/bin`（→ `~/.local/lib/node_modules`） | v24.21.0 | **0.2.1-rc.4** | 有 |
| `~/.local/node22/bin` | node22 | 0.1.5-rc.3 | 无 |
| `/usr/local/bin/node`（系统） | v22.22.1 | — | — |

`~/.local/bin` 是完整 node24 环境（node/npm/pnpm/dsh 配对）。用 0.1.5-rc.3 的 dsh 去跑 0.2.1-rc.4 的 `profiles/web`，`dsh-agent-preset` 必然找不到 —— 这是版本错配的必然结果，不是插件缺失。

## 3. 根因：`.bashrc` 前置 node22，`.local/bin` 只在 `.profile` 里

- `~/.bashrc:125` 原本：`export PATH="$HOME/.local/node22/bin:$PATH"`（**前置**，压过一切）
- `~/.local/bin` 的 PATH 只在 `~/.profile` 中追加
- **图形终端/普通终端是交互非 login shell：只读 `.bashrc`，不读 `.profile`**

结论：`.local/bin` 在该环境下根本不在 PATH 中，`dsh` 落到 `.local/node22/bin/dsh` = 0.1.5-rc.3。

## 4. 修复（已落地并验收）

```bash
# ~/.bashrc:125（备份 ~/.bashrc.bak-20261029-dshpath）
- export PATH="$HOME/.local/node22/bin:$PATH"
+ export PATH="$HOME/.local/bin:$PATH:$HOME/.local/node22/bin"
```

`bash -ic` 复验：`which dsh` = `~/.local/bin/dsh`，`dsh --version` = 0.2.1-rc.4，`node -v` = v24.21.0；裸 `dsh web --no-open` 一次起、零报错。

## 5. 验证方法铁律（本次最大教训）

前两轮用 `ssh tianque 'bash -lc ...'` 验证，**login shell 会读 `~/.profile`，用户终端不读**，两个环境不同构，于是连续两轮误判「已修好」。

- 验证必须在与用户终端同构的环境：`ssh ... 'bash -ic "<cmd>"'`，或让用户在真终端里跑。
- **先看报错里的绝对路径，再看报错内容**：路径不同即意味着命中的是另一套安装/另一个 profile。
- `startup failed` ≠ `incompatible`：required 插件单点失败（如 EADDRINUSE）会被放大成全屏级联 waiting，先看 required 那条 `Error:`。

## 6. 最终端口分工（用户明确要求：3080 留给手动 `dsh web`）

| 端口 | 归属 | 验收 |
|---|---|---|
| **3080** | 用户终端手动 `dsh web`（默认端口，保留不占用） | `curl` → 401（存活） |
| 3081 | `dsh-web.service`（systemd，enabled） | `curl` → 401 |
| 3082 | `dsh-tunnel.service` → Windows `192.168.243.1:3080` | 隧道 LISTEN 但 3080 无后端 → `Empty reply from server`（curl 000） |

- `dsh-web.service` 与 `dsh-tunnel.service` 的 `Description` 已同步改准（原描述仍写 "port 3080"，会误导下次排查）。
- **3080 与 3081 并存不冲突**（同时起两个实例均返回 401），但两者共享同一 `profiles/web`，session 库是并发的；只保留手动实例可 `systemctl --user disable --now dsh-web.service`。
- 3082 的 000 不是修改导致的回归：Windows 侧 `netstat` 无任何 30xx LISTENING，node 进程只有 `mcp-goat-quota.mjs` 与 `billion-context`（18787），故隧道转发到空后端。Windows 起 `dsh web` 后即可用；若实际端口不同，只改 `-L 3082:127.0.0.1:<真实端口>` 一处。

## 7. 附带踩坑

- `pkill -f "dsh web --no-open"` 会杀掉执行它的 ssh 会话自身（命令行字符串自匹配）；正确写法 `pkill -f "[d]sh web"`。
- 用户口述的「3038 端口」按上下文理解为 3080（`dsh web` 默认端口），执行前先确认映射，不要照字面改。
