# NeoForge 21.1.236 → 21.1.244 升级评估（2026-10-04）

## 症状与用户约束

- 该 Minecraft 1.21.1 整合包启动报错，要求 NeoForge build ≥ 21.1.244；实例原为 `21.1.236`。
- 用户明确要求 **不要升级游戏版本**（理由：Create / 机械动力只能在这个游戏版本上跑）。
- 因此本次排查的核心问题：报错要求的 `21.1.244` 是 MC 版本还是 mod loader build。

## 关键机制：NeoForge 版本号语义（可复用结论）

NeoForge 版本号形如 `<MC minor>.<MC patch>.<build>` ⇒ `21.1.x` 全体对应 **MC 1.21.1**，只有第三段 build 在变。
因此「升级到 21.1.244」不改变 MC 版本号，也不改变任何 mod 面对的 API 版本号。

installer 为 21.1.244 生成的 version json 中，游戏参数逐字为：

```
--fml.neoForgeVersion 21.1.244
--fml.fmlVersion       4.0.43            ← 与 21.1.236 完全相同
--fml.mcVersion        1.21.1            ← 仍是 1.21.1
--fml.neoFormVersion   20240808.144430   ← 与 21.1.236 一字不差
```

## 取证方法：mod 兼容区间读 jar 内的 toml

- 判定某 mod 支持哪个 loader build，**必须读 jar 内 `META-INF/neoforge.mods.toml` 的依赖声明**；文件名、发布页摘要都取不到区间（本轮实测：先从 mod 页面读依赖，7 个 jei 版本全部 `<未取到>`，改用 `python` 的 zipfile 直接读 jar 才拿到区间）。
- 读法：`python -c` + `zipfile.ZipFile(...).read('META-INF/neoforge.mods.toml')`；本地有 `/usr/bin/unzip` 与 `C:\Users\27063\AppData\Local\Programs\Python\Python313\python`。
- 把下载文件存成 `*.jar_` 后缀不影响 zipfile 读取（本轮 7 个 jei 均如此解出）。

## 两条路线与代价（版本上限来源已定位）

- 整合包对 neoforge 的要求区间交集是 **`[21.1.244, 21.2.0)`**，21.1.244 正好落在里面；唯一上限来自 `shield_generators-1.4.0.jar` 的 `[21.1.228, 21.2.0)`。
- **A：原地升 NeoForge 21.1.236 → 21.1.244** — MC 1.21.1 不变、Create 6.0.10（`create-1.21.1-6.0.10.jar`）不变，`mods/` `saves/` `config/` 不动，保留 flightblocks + compat。需要改实例 json 的 3 处（`--fml.neoForgeVersion`、asm `9.8→9.10.1` 的 module path、对应 libraries 条目），改前备份 json。
- **B：完全不碰 NeoForge（留在 21.1.236）** — 必须删/禁用 `flightblocks-sable-compat-1.0.1.jar`（自制 patch，只有一个版本，硬要 ≥21.1.244，无更老兼容版）⇒ 飞行方块在 Sable sublevel 里失效；且 jei 必须从 `19.57.0.450` 降到 `19.25.1.331`（已下载校验）⇒ 退回约半年前的 jei，丢失 compat 功能。

## 容易误判的一点

该整合包**当前在 21.1.236 上已经起不来**，且不是新加 mod 所致：`mods/latest.log`（Aug 29）里 jei 已报 `[21.1.238,)` 不满足。所以路线 B 不是「保持现状」，而是「降 jei 才能恢复可启动」。
