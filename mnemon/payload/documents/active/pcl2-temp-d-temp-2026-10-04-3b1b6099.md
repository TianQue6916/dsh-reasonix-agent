# PCL2 TEMP 迁移落地验证 + 旧备份清理（2026-10-04）

## 背景与用户指令

承接文档 **422e3c22**（PCL2 导出把 `AppData\Local\Temp\PCL\TaskTemp` 撑到 27.7 GB 撑爆 C 盘的诊断与修复方案）。
用户指令（m00302 逐字）："CL 导出时把 %TEMP% 当中间工作目录——这才是 10/03 晚上炸 C 盘的根因，不修的话下次导出 27GB 还会再来一遍。这个修一下,然后清理备份吧,保证我正在玩的存档别坏了就修"。

## 一、修复落地

`HKCU\Environment`：

| 值 | 改前 | 改后 |
|---|---|---|
| `TEMP` | `%USERPROFILE%\AppData\Local\Temp`（`REG_EXPAND_SZ`） | `D:\Temp`（`REG_SZ`） |
| `TMP` | 同上 | `D:\Temp` |

## 二、为什么不用注销就已生效（本次最值得记的机制）

`[Environment]::SetEnvironmentVariable(name, value, 'User')` 不只是写注册表：它会广播
`SendMessageTimeout(HWND_BROADCAST, WM_SETTINGCHANGE, 0, "Environment")`。`explorer.exe` 监听该消息，
收到后**重新读取自己的环境块**。因此此后任何由 explorer 拉起的进程（双击快捷方式即此路径）继承到新值 —— 无需注销/重启。
**已在运行的进程不会改变**：PCL（PID 9056，`10/03 23:35:11` 启动）环境块冻结在旧值，关掉重开即可，之后
`Path.GetTempPath()` 返回 `D:\Temp\`，`TaskTemp` 落到 `D:\Temp\PCL\TaskTemp\`，峰值撑的是 D 盘而非 C 盘。

## 三、验证方法：有效 vs 无效（可复用教训）

- **无效测法**：用 `Start-Process` 起探针。父进程是 PowerShell 而不是 explorer，沿继承链上溯必然拿到旧环境 ⇒ **零信息量**。
- **有效测法**：让**正在运行的 explorer 自己**执行探针，即 `explorer.exe <probe.cmd>`。实测探针看到
  `TEMP=D:\Temp`、`TMP=D:\Temp`。
- **直击真实 API**：直接调用 PCL 内部实际使用的 `Path.GetTempPath()` → `D:\Temp\`。
- **旁证**：`D:\Temp` 下自行长出 `.ses`（00:45）与 `goat-usage-cache.json`（00:43），说明已有其他程序在往新路径写。
- 自己踩的坑：`Stop-Process -Name explorer -Force` 实际**没杀掉** explorer（PID 14472 自 `10/03 23:11:35` 起未变；
  当前 shell `is elevated: False`），而且这一步本来就不必要 —— 刷新环境块不需要重启 explorer。
- 复验命令：`reg query HKCU\Environment /v TEMP`；重开 PCL 后 `Get-ChildItem D:\Temp\PCL -Recurse -Depth 2`。
  若 `C:\Users\27063\AppData\Local\Temp\PCL` 仍长新文件，说明还有第二条写死 C 盘的路径。

## 五、被撤销的删除与「不可重建数据」判据（重要）

原计划删 `journeymap\data\`（10.57 GB，计在 11 GB 的 `journeymap\` 下）。侦察发现该子树混有两类数据：

- 瓦片 LOD 缓存：**可重建**。
- 手工标注的路点：**不可重建** —— 115 个文件，形如
  `journeymap\data\mp\offline\waypoints\backup\<日期>\WaypointData_backup_MM-DD-YYYY_HH-MM-SS.dat`，
  以及 `journeymap\config\6.0\journeymap.waypoint.config`。

**判据：可重建与不可重建数据混在同一子树时，不得整目录删除；须先把 `waypoints\` 与 `config\` 单独摘出。**
当前 `journeymap\` 原样保留。
