# S5 后 13~21 秒自启：WoL 定论被推翻后的续查（2026-10-25）

**关联文档**：`f7c9342c-8f53-4d5f-a8b7-405828718eae`（《关机后 13 秒自动开机（S5 后冷启动）定位为 Realtek 网卡 Wake-on-Pattern》）。
本篇不修改那篇，只记录**推翻其结论的两条用户事实**与由此产生的新假说、方案取舍。结论状态：**假说未闭环**，决定性实验尚未执行。

---

## 一、原定论为何作废（两条用户陈述，非推断）

| 原结论 | 推翻它的事实 | 来源 |
|---|---|---|
| 元凶是 Realtek 网卡 Wake-on-Pattern（`*WakeOnPattern=开启`） | 用户澄清：**「官方说明文档表示没有」** —— 该主板官方文档确认不支持 WoL | 用户原话 |
| S5 自启是网卡魔术包/模式唤醒 | 用户澄清：**「是我主动开的通电自启」**；**「我会远程开机,需要这个通电自启」** | 用户原话 |

配套的自我证伪：Realtek 驱动 UI 里 `S5WakeOnLan = 开启` **不能证明固件支持 S5 WoL** —— 这套 NDIS 高级属性由驱动自带，即使固件/EC 未实现唤醒线，UI 照样显示「开启」。同理 `Win32_ComputerSystem.WakeUpType = 6`（LAN Remote）可能是 BIOS 写死的常量，不构成证据。

**教训（可复用）**：`*WakeOnPattern` / `S5WakeOnLan` 这类注册表值与驱动 UI 只是**能力声明**，不是固件实现证明；判断 S5 唤醒必须用「发魔术包实测」或厂商文档，不能读注册表。

## 二、新工作假说：EC 误判 AC_PRESENT 的 0→1 边沿

用户补充观测：**「关机的时候电源状态一直是开,没有切换」**——适配器始终插着、插座未动。这不与假说矛盾，因为 `AC_PRESENT` 不是导线通断，而是带阈值与去抖窗口的比较器输出：

```
适配器 19.5V → 分压 → EC 的 ADC 引脚 → 阈值判定 → AC_PRESENT(0/1)
                                        （中间有秒级~十几秒去抖窗口）
```

机理链（边沿触发，非电平触发）：

```
① 关机 → S5，主电源断，负载骤降（几十瓦 → 近 0）
② 适配器/DC-DC 由重载转轻载，输出出现跌落-恢复（PD 充电器空载打嗝最常见）
③ EC 采到的分压值瞬间越过判定阈值
④ EC 判定 AC_PRESENT 出现 0→1 边沿
⑤ 固件策略 = Power On ⇒ 立刻拉 PS_ON# 加电，完整冷启动
```

**13~21 秒的固定延迟 = 第 ②③ 步的时间尺度**（负载切换 → 输出稳定 → 去抖窗口走完），不是"等唤醒源"也不是"定时器"。这解释了此前解释不了的三点：概率约 35%、`08-28 / 09-11 / 09-25` 连起 2~3 次（同一瞬态条件复现）、少数离群 31s/33s/59s（适配器稳定档位不同）。

**为什么日志里看不到原因**：S5 状态下 OS 不运行，EC 侧的事件 Windows 一个字节都记不到。日志只覆盖 S0，事故发生在 S5 —— 这是该 bug 最难查的根因。

### 支撑数据（本轮实测）

- `Kernel-Power 105`（ACPI 电源更改）60 天共 **9 条**，其中 **6 条贴着关机/开机时刻**：
  - 08-27 21:59:55 / 22:00:00（**配对，间隔 5 秒** = AC 掉了 5 秒又回来）
  - 09-03 23:14:12 / 23:14:17（同样配对）
  - 09-06 11:50:53（boot 11:51:05 前 12 秒）
  - 09-13 01:24:57（shutdown 01:25:11 前 14 秒）
  - 09-14 00:38:22（shutdown 00:39:00 前 38 秒）
  - 10-12 01:46:30（Kernel-Power 109 开始后 9 秒）
- 判读边界：105 只有 9 条而自启 26 次，因为 **S5 下的边沿 OS 记录不到** ⇒ 105 是强线索，不是结论。

## 三、硬约束：用户需求与原定论同源，不能靠改 BIOS 选项两全

用户真实用途是**远程开机（智能插座断电→通电）**，因此：

| BIOS 策略 | 断电前运行中 | 断电前已关机 | 能否满足用户 |
|---|---|---|---|
| `Power On`（当前） | 来电开机 ✓ | **来电也开机 ✗（= 本 bug）** | 必须保留 |
| `Power Off` | 不开机 ✗ | 不开机 ✓ | 杀掉远程开机 |
| `Last State` | 来电开机 ✓ | 保持关机 ✓ | **同样杀掉远程开机** |

关键更正：`Last State` 曾被当作"两全方案"推荐，**是错的** —— 它恰在「机器已关机 → 通电 → 希望它起来」这一场景下保持关机，而这正是用户远程开机的场景。**`Power On` 与「关机后不自启」在固件逻辑上是同一条件的两面**，只能选代价。

同理，笔记本 + 电池在位时，「停电恢复自动开机」这个 `Power On` 的经典用途**并不成立**（停电时切电池继续跑，压根不关机）；该功能在用户机器上唯一真实的用处就是智能插座远程开机。

## 四、方案取舍（按彻底性排序，均待用户拍板）

| 方案 | 保住远程开机 | 消除自启 | 彻底性 | 代价/风险 |
|---|---|---|---|---|
| **A. 关机完成后插座断电** | ✓ | ✓ | **物理上消灭假边沿** | 断电须落在关机后 ~15 秒窗口内；需插座支持（多数防抖 ≥30 秒则来不及）；**插座上不能串路由器/光猫**，否则远程回连失效 |
| B. OS 侧「假自启自愈」 | ✓ | ✓（多跑一轮开关机） | 事后补救 | 计划任务；每次自启白跑 ~40 秒 |
| C. 休眠(S4) 代替关机 | ✓ | ✗ 大概率无效 | — | S4 与 S5 对 EC/适配器同构（主电源都断），假边沿照样产生 |
| D. 接受（再关一次） | ✓ | ✗ | — | 用户当前实际做法 |

**A 的原理值得记住**：它不改信号，而是让错误信号没有产生的物理条件 —— 插座断电后 `+5VSB` 消失、EC 停止工作，假边沿无从产生；而远程开机时的通电是**真边沿**，正是开这个功能的初衷。

**B 的判据**（时间特征足够干净，无需关机时写状态）：

```
开机 → 读最近 Kernel-Power 109 (Shutdown Off) 时间
     → 若 (本次 boot − 109) < 60 秒 ⇒ 判定假自启 ⇒ shutdown /s
```

假自启固定落在 13~21 秒，60 秒阈值有 3 倍余量；远程开机时上次正常关机通常已是几十分钟/几小时前。唯一误杀边界：手动关机后 60 秒内反悔 —— 用倒计时 + `shutdown /a` 兜住。

### 已排除 / 已下调的路线

- **休眠替代关机**：原先报"可能是真两全"，后被更正为期望值偏低（见上表 C）。实测佐证：`hiberfil.sys` = 12.69 GB（RAM 31.73 GB 的 40%，默认 reduced 配置），但 **60 天 BootType 分布 `0x0`×68 / `0x1`×0 —— 从未真正用 S4 恢复过一次**，所以 hiberfile 存在与自启无关，不必再怀疑它是元凶。`HiberbootEnabled = 0`（快速启动已被策略禁用）。
- **RTC 定时唤醒 / USB-HID S5 唤醒**：仅在"改 BIOS 策略后仍自启"时才有必要转向。

## 五、待执行的决定性实验（未做，结论因此未闭环）

**实验 0（1 分钟，顺带证伪 WoL 线索）**：手动关机 → 按电源键开机 → 查 `(Get-CimInstance Win32_ComputerSystem).WakeUpType`。变 `7`(Power Switch) ⇒ 该字段动态，原 `6` 有意义；仍为 `6` ⇒ BIOS 写死，线索作废。

**实验 1（决定性）**：
1. 正常关机不碰电源，等 60 秒 → 预期约 1/3 概率 15-20 秒自启
2. 关机后立刻拔适配器（只留电池），等 60 秒 → 预期**不自启**（AC_PRESENT 恒 0，无边沿）
3. 在 ② 状态下插回适配器 → 预期**立刻自启**（同时证明通电自启功能正常，触发源就是 AC 边沿）
若 ② 拔了适配器仍自启 ⇒ 不是 AC 链条，转查电源键/EC。

**实验 2（改策略后验收探针）**：

```powershell
$ev = Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddDays(-3); Id=109,27} | Sort-Object TimeCreated
for ($i=0; $i -lt $ev.Count; $i++) {
  if ($ev[$i].Id -eq 109) {
    $nx = $ev | Where-Object { $_.Id -eq 27 -and $_.TimeCreated -gt $ev[$i].TimeCreated } | Select-Object -First 1
    if ($nx) { "{0:MM-dd HH:mm:ss} off->boot = {1:N0}s" -f $ev[$i].TimeCreated, ($nx.TimeCreated-$ev[$i].TimeCreated).TotalSeconds }
  }
}
```

判据：连续 5 次关机不再出现 ≤120 秒的 `off->boot`。

## 六、仍缺的用户输入（OS 读不到，必须问）

1. BIOS 里 `Power On after AC Loss` 一类的**确切名字与全部可选值**（同方 Uniwill 模具的 Insyde BIOS 常在 `Advanced → Power Management`；别名：`State After G3` / `Restore on AC Power Loss` / `AC Back Function`）。仅有 `On`/`Off` 还是也有 `Last State`、有无 `AC Recovery Delay` / 去抖选项，决定 A 之外是否还有固件侧解法；顺带看 BIOS 是否有更新（当前 `N.1.21MRO16`，2025-07-24）。
2. 供电链路：原装圆口适配器还是 Type-C PD；是否过排插、排插上还挂什么（带继电器/压缩机的设备是常见假边沿来源）。
3. 智能插座型号与是否支持「功率 < 3 W 持续 10 秒 → 断电」这类自动化，以及插座上是否串了路由器 —— 直接决定方案 A 可行性。
