# 备份 repo 缩容：四条路径的实测数字与保留策略候选

> 关联文档：`85170571-414b-4b3c-bc68-f2be7ff00363`（push 每天失败的根因 + 228MB ONNX 双仓库污染，含 `reflog expire` 把 `.git` 762 MB → 537 MB、`size-pack: 535.82 MiB` 的同一基线）；
> `9b946245-989a-40ea-ad41-9fc6aa953d0c`（2026-10-26 cb70ace 瘦身实测 + 当时**放弃** filter-repo 的判据）。
> 本篇是那篇「放弃 filter-repo」判据的**实测补充**：真跑了 filter-repo，拿到三档确切体积。

## 结论先行

537 MB 里只有 **27 MB 是「当前的你」**，其余 508 MB 是过去 4 个月的历史版本。
`git rm --cached` / `.gitignore` 只影响未来，**动不了已进 pack 的 blob**；要回收只能重写历史或让它不可达后 `gc --prune=now`。

## 实测（在 `/tmp/frexp` 的 mirror clone 副本上跑，原仓库未动）

| 做法 | `.git` pack | 相对现状 | 耗时 |
|---|---|---|---|
| 现状（46 commits 全历史） | **535.82 MiB** | — | — |
| `git filter-repo --strip-blobs-bigger-than 10M` | **325.03 MiB** | −39% | 3.3 s |
| `git filter-repo --strip-blobs-bigger-than 1M` | **258.15 MiB** | −52% | — |
| 只保留当前树、0 历史（`commit-tree` 重建） | **26.91 MiB** | −95% | — |

- `clone --mirror` 副本本身：536 M `m.git`，1.27 s。
- strip >10M 后 `in-pack: 7515`，repack/clean 共 2.97 s。
- 「单快照（仅当前树）」的等价社区做法是 orphan branch：`git checkout --orphan` → `add -A` → `commit` → 删旧分支 → `gc`。

## 体积归因（为什么这么大）

- 全 refs：**5004 个唯一 blob，870.4 MiB**。分布：>100M 一个（228.2 MiB，`dsh/speech-to-text/sensevoice/models/sensevoice-onnx/model.int8.onnx`）、10–100M 8 个（138.3 MiB，含 `dsh/.backup/dsh-0.1.0-rc.6.tar.zst` 50.9 MiB 与 5 个 11.9 MiB 的 `mnemon/payload/data/*/mnemon.db`）、1–10M 78 个、<1M 4917 个（340.5 MiB）。
- 剥掉 >10M 的 blob：870 MiB → 504 MiB（压缩前）。
- 按顶层目录（历史首次引入 blob 量）：`dsh` 644.7 / `mnemon` 90.4 / `reasonix` 62.2 / `goat-gateway` 19.0 MiB。
- 单 commit 首次引入量 Top4：`f3fe6ba` 231.81、`7beca8b` 203.02、`9075047` 141.85、`8a5f029` 55.03 MiB —— 早期几次「把整个工作区塞进去」的镜像提交，一次贡献约 40%。44 个 commit 合计 892.3 MiB。
- 全 refs 46 commits，跨度 2026-06-15 → 2026-11-01；`master` 31 + `mnemon-sync` 12。
- `mnemon.db` 反复出现：`60c9a1d`/`6e78407`/`dc3188a`/`1356c65`… 全是 `origin/mnemon-sync` 的 47 分钟一次 Mnemon sync，每次全量写一份 11.9 MiB SQLite。

## 机制判据（为什么「降频率」对未来有效、对过去无效）

`.git ≈ Σ_commit Σ_改动文件 |zlib(file)|`。commit 是 snapshot 语义不是 diff 语义，没变的文件共享旧 blob，所以 commit 本身几乎不花钱（实测 1000 个 4 KB 文件：1 次 commit 的 `.git` 4.04 MB；再改 100 次+提交 100 次只涨到 6.83 MB，边际 ≈197 ms）。但 blob 内容寻址且一经历史即永久占位，且存整文件不存增量。
⇒ 对 append-only 大文件（`memory/*.jsonl`、每次全量重写的 `mnemon.db`），**历史体积 ≈ 文件大小 × commit 次数**，与提交频率严格线性。git 没有 prune（restic/borg/kopia 靠 `forget --keep-daily…` + `prune` 解决），「忘记」只能重写全部历史。

## 保留策略三档（待用户拍板；当前推荐 B）

| 方案 | 做法 | `.git` 预期 | 丢失 |
|---|---|---|---|
| **A 只剥大文件** | `filter-repo --strip-blobs-bigger-than 10M` + force push | 325 MiB（实测） | 历史里的 ONNX / tar.zst / mnemon.db 旧版本；代码与文本历史全留 |
| **B 剥大文件 + 压 30 天前历史** | A + squash 30 天前的 commit（保留最近 30 天逐日 diff） | 估计 50–100 MiB（**未实测**） | 30 天以前的逐日 diff |
| **C 单快照 + 归档** | 只留当前树，历史整体导 bundle 放本地磁盘，每季度重建 | 27 MiB（实测） | git 里的历史（bundle 里还在，不能 `git log`） |

推荐 B 的理由：A 的收益被「历史里的文本版本」吃掉大半；C 会让「上周配置长什么样」只能翻 bundle。B 是唯一同时满足「能回滚一个月」和「体积可控」的。
A 以外的实测建议：动真格前先在 `/tmp` 副本上复跑一遍，B 的数字需要真跑才准。

## 顺手可修的两件独立事项

1. `origin/mnemon-sync` 每次 sync 全量存 11.9 MB SQLite —— **数据库文件不该进 git**（页对齐二进制，zlib 压不动，每次全量）。该分支要么只留最新一个 commit，要么整个从备份 repo 移除、改由 mnemon 自己的 payload 目录管。
2. `~/.dsh` 自己的 `.git` 是 346 MB，其中 228 MB 也是那个 ONNX ⇒ 同一剥除策略两边都要跑（`~/.dsh` 是工作仓库，重写会改 hash，但无远端镜像，代价更小）。参考同一基线：`~/.dsh` git status 104–112 ms、`D:\Desktop\工具箱\reasonix-ops\repo` 146 ms/次，status 耗时不是瓶颈。
