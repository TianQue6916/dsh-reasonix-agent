# dsh 调用问题根因与修复（2026-09-11）

## 现象
用户报告：agent 调用主力机 dsh 时「通知也没了」+「经常失败」。

## 根因 1：通知没丢，是被显式关闭
- 通知链路完好：本机 `notify-send` + 主力机反向 SSH 均实测发出横幅。
- 真因：9/11 会话里 agent 的 dsh 调用**全部 9 处都带 `--no-notify`**（该开关就是关横幅用的）。
- 修复：dsh-remote 头部 + dsh-gate SKILL 加铁律「除非用户明确要求静默，禁止 --no-notify」。

## 根因 2：长任务失败 = 同步调用在 ~167s 丢失结果（决定性对照）
同一任务/模型/effort 的对照：
| 方式 | 结果 | 耗时 | 输出 |
|---|---|---|---|
| 同步 dsh-remote（SSH 前台） | ❌ rc=1 | 167s | **0 字节（stdout/stderr 全空）** |
| `dsh-remote --async`（schtasks 脱离 SSH） | ✅ done | **192s** | 6426 字节 |

已逐项排除：
- **上游/代理**：同一 prompt 用 curl 直打 `api.commandcode.ai`（走 dev-sidecar 代理）→ **148s / HTTP 200 / 10.37MB 成功**
- **Node 内存**：`NODE_OPTIONS=--max-old-space-size=8192` 无效，仍 167s rc=1
- **SSH 保活**：IP 字面量方式 SSH 空跑 **210s 仍返回 rc=0** → 非 TCP/保活超时
- **参数传递/任务长度/并发**：手动直调 dsh（绕过 dsh-remote）同样 168s rc=1；2462 字符占位任务 off 成功
- 失败耗时刚性集中在 164–181s；成功 4–199s

**结论：根因在同步调用路径（SSH 会话进程树），不在 dsh/上游/代理/内存。长任务一律 `--async`。**

## 根因 3（附带，比上面更隐蔽）：`-e/--effort` 从未生效
- 主力机 `~/.dsh/settings.yaml` 的 `agent-default-model:` 段**没有 `reasoningEffort:` 键**，
  而 `dsh-gate-conc.ps1` 只用 `-replace '(?m)^  reasoningEffort: .*$'` → **静默空转**。
- 证据：`-e high` 与 `-e off` 生成的 settings 副本 **SHA256 完全相同**（ED477C5B…）。
  「全任务统一 v4.1 flash、用 -e 区分算力」的设计此前是空文。
- 修复：settings.yaml 补 `reasoningEffort: high`（14616→14640B）；脚本改为「按键存在性判断」。
- 验证：`-e off` → hash C895E599…，`-e max` → hash D520EF91…，**两副本 hash 不同** ✔

## 踩坑：DUPLICATE_KEY（自引入，已修）
第一版修复用「-replace 前后是否变化」判断键是否存在；当 `-Effort` 恰好等于原值（high）时替换结果不变 → 误判为「无该键」→ 重复插入 →
`settings-file: invalid document ... DUPLICATE_KEY at line 7` → dsh 启动即失败（2s、4158B 报错）。
**必须用 `-match` 判断存在性，不能靠替换前后差异。**

## 已落地改动
- 主力机 `settings.yaml`：补 `reasoningEffort: high`
- 主力机 `dsh-gate-conc.ps1`：effort 存在性判断 + 校验；失败可见化（`note` 记 rc/耗时/输出字节，落盘 `.diag.txt` 含原始 stdout+stderr）
- 本机 `dsh-remote`：改用 ssh 别名 `tqjq`（继承 ServerAliveInterval 30）、失败时提示诊断位置、注释加 --no-notify 禁令
- 本机 `skills/dsh-gate/SKILL.md`：写入「长任务必须 --async」「禁止随手 --no-notify」「-e 修复说明」三条硬约束
- 备份：本机 `~/backups/20260911-dshfix/`；主力机 `C:\Users\27063\backups\20260911-dshfix\`
