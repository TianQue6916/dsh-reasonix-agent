# GitHub 加速体系（2026-09-27 建成）

## 一、三条路径（按场景分工，互不干扰）

| 场景 | 走什么 | 配置位置 | 自动程度 |
|---|---|---|---|
| `git clone/fetch` | **由 `~/.ghmirror-git` 决定（每日/边沿选优，非固定）** | `~/.gitconfig` 的 `url.<base>.insteadOf`（由 watch-agent 写入） | ✅ 自动选优 + 有 repair 回写 |
| release、大文件 | `~/.ghmirror`（每日选优） | `~/.bashrc` + PS profile 的 `ghurl`/`ghdl`/`ghdlx` | ⚠️ 要手动敲命令 |
| 浏览器 | dev-sidecar（SNI 伪装 + 脚本注入） | `~/.dev-sidecar/config.json` | ✅ 它自己的机制 |

⚠️ **push 不受影响**：13 个课程仓 remote 全是 SSH（`git@github.com:`），不匹配 https 重写规则。

## 二、镜像生态：三类分化（核心事实，别再混用）

1. **支持 Range（返回 206）** — 20/25，可多线程 + 可断点续传
2. **不支持 Range（返回 200）** — 如 `git.yylx.win`，单连接 1888 KB/s「最唬人」，
   但 aria2 会退化成 `CN:1` 单连接，且无法续传
3. **不支持 clone** — `gh-proxy.org`、`ghproxy.monkeyray.net`、`git.yylx.win`：
   `git ls-remote` 能过，**完整 clone 失败**

**铁律：`git ls-remote` 通过 ≠ clone 可用。** 验证必须用真实 `clone --depth 1`（octocat/Hello-World 这种小仓库）。

**速度波动 36 倍**：同一个 `gh-proxy.com` 当天测到 85 KB/s ↔ 3075 KB/s。单次测量不可信，这是每天重探的理由。

**aria2 在 GitHub 镜像场景无增益（根因）**：gh-proxy 返回 `206 + Content-Range`
但**不返回 `Accept-Ranges: bytes`** —— aria2 靠这个头才敢分片。GitHub 官方直连有这个头。

## 四、自动化：已实现「打开软件即自动就位」（2026-09-27 实测闭环）

**核心是一个常驻守护 `watch-agent.ps1`**，它用两种触发配合，覆盖了纯边沿检测的盲区：

| 触发 | 条件 | 动作 | 耗时 |
|---|---|---|---|
| **状态边沿** | dev-sidecar 进程由无到有 / 系统代理由关到开 | **完整 sync**：探测 25 个镜像 → 真实 clone 测试 → 写 gitconfig | ~90s |
| **健康巡检** | 每 60s 检查 `http.proxy` 是否被写回 / `insteadOf` 是否丢失 / `~/.ghmirror` 是否在 | **轻量 repair**：不联网，直接用 `~/.ghmirror-git` 重写 git 配置 | **~3s** |

**为什么需要健康巡检**：快速重启时"进程消失→重现"会落在两次轮询之间，边沿检测**必然漏掉**（实测复现过）。
而 dev-sidecar 覆写 gitconfig 是高频小事故 —— 用"完整探测"这种重武器去修它是设计错误。

节流：完整 sync ≥ 60s、repair ≥ 90s，避免抖动时反复跑。

**实测闭环证据**：
```
11:17:40  edge <init> -> True|1 ; FULL sync scheduled
11:19:12  full sync finished
11:20:02  health check FAILED ; repair scheduled     ← 手工注入 http.proxy=31180 后被抓到
11:20:05  repair finished                            ← 3 秒复原
```

**你现在的操作量：零。** 打开 dev-sidecar 即可。`ghdl` 只在"下载大文件"时手动敲。

## 六、踩过的 8 个坑（重踩代价高）

1. **dev-sidecar 每次启动重写 `~/.gitconfig` + `~/.npmrc`**（把 proxy 指回 31180/31181、`sslVerify=false`）
   → 手改必被覆盖；正解是 **URL 级 `http.<url>.proxy`**（优先级高于全局）。见另一条记忆。
2. **PowerShell 5.1 的 `*>> $log` 写 UTF-16**，与 `Add-Content -Encoding utf8` 混用 → 日志乱码。
   统一走 `[System.IO.File]::AppendAllText($log, $t, [UTF8Encoding]::new($false))`。
3. **`Write-Host` 不进 pipeline** → `Out-String` 抓不到，计划任务日志是空的。全改 `Write-Output`。
4. **`$results = foreach (...) { Write-Output ... }` 会把输出吞进 `$results`** → 循环内只收集对象，输出放循环外。
5. **curl `-C -`（续传）与 `-J`（remote-header-name）不能共存** → 顺手加参数会让 `ghdl` **100% 失效**。
   正解是 `-O -C -`。**教训：任何加参数都必须跑一次端到端。**
6. **python 写 PS 脚本时 ``/`\T` 被当转义** → 路径里 `ria2` 变 BEL 字符，路径被毁。用 **raw string**。
7. **`/dev/null` 在 Windows 原生 curl 下无效**（python subprocess 调的是 `C:\Windows\System32\curl.exe`，
   不是 MSYS 的 curl）→ 用 `os.devnull`（`nul`）。
8. **镜像探测的超时与取样大小必须匹配**：1MB 取样 + 6s 超时 → 在 85 KB/s 的链路下全部超时返回 `000`，
   看起来像"所有镜像都挂了"。现用 **256KB / 10s**。

## 九、watch-agent 的四个设计要点（改它之前先读）

1. **必须同时有边沿 + 巡检**。只用边沿 → 快速重启漏检（实测）；只用巡检 → "刚打开软件"要等最多 60s 才有反应。
2. **修复要分级**。覆写配置是高频小事故 → 用秒级 repair；镜像选优是低频重活 → 只在边沿/每日做。
3. **PS 5.1 传空字符串给原生 exe 会被丢弃** → 写 git 空 proxy 必须用 `'""'`（否则 `error: wrong number of arguments`，静默失效）。
4. **多条 `url.*.insteadOf` 共存时 git 只认第一条** → 每次必须先全清再写，否则镜像切换静默失效。

## 【2026-09-27 更正】原表写「git 走 `gh-proxy.com` 固定」是错的

三处实测，system 内部自洽，是**文档没跟上自动选优**：

```
~/.ghmirror      = https://gh-proxy.com/            (下载用)   11:18 写
~/.ghmirror-git  = https://edgeone.gh-proxy.org/    (git 用)   11:20 写
gitconfig url.*.insteadOf = edgeone.gh-proxy.org    ← 与 ~/.ghmirror-git 一致
```

→ git 侧**不是固定值**，读 `~/.ghmirror-git` 才是真相；下载侧读 `~/.ghmirror`。
本表第 52 行「repair 用 `~/.ghmirror-git` 重写」本来是对的，第 20 行与之矛盾。

**复验**：`cat ~/.ghmirror-git; git config --global --get-regexp 'url\..*insteadOf'`（两者必须一致）
