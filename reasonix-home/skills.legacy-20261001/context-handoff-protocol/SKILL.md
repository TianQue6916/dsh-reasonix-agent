# Reasonix 会话分支 · 上下文交接协议

## 何时自动触发

- 用户要「分出去」一个会话（隔离工作区 / 分支会话 / delivery worktree）
- 用户抱怨：「分出去之后合并，上下文没回来」「合并工作区分支后对话丢了」「合并只合并了文件」
- 用户准备创建 delivery / isolated worktree，且任务会跨越多个回合
- 界面出现：「合并工作区分支」「领先 N · 落后 N」「已创建分支会话 {session}」

## 一、先把机制说清楚（为什么必须用文件当媒介）

会话的**两层隔离**是分开的，Merge-Back 只管第一层：

| 层 | 隔离机制 | 物理位置 | Merge-Back 是否处理 |
|---|---|---|---|
| **文件** | git worktree | `%LOCALAPPDATA%\reasonix\worktrees\<hash>\<id>\<name>\` | ✅ 处理 |
| **会话** | 按工作区路径分桶 | `%APPDATA%\reasonix\projects\<路径slug>\` + `desktop-sessions-v5\by-id\<24位hex>\` | ❌ **不处理** |

**代码级证据**（Reasonix v1.38.10）：

- `assets\WorktreeMergeModal-*.js` 全文 8320 字符中，`session` / `topic` / `context` / `conversation` / `history` 各出现 **0 次**，只有 `worktreeBranch`（3 次）
- 合并 pipeline 全为 git 操作：
  `PrepareWorktreeMerge → InspectWorktreeMerge → MergeWorktreeBack → FinalizeWorktreeMerge → CloseMergedWorktreeTab`
  最后一步是**关掉分支 tab**，不是搬走会话
- bridge 中 `ForkSession`（分叉）存在，而 `mergeSession` / `carrySession` **命中 0 次** —— 会话只有单向分叉，没有回并通道
- 实测分桶：source 桶 `topic 数 = 0`，worktree 桶 `topic 数 = 1`（`topic_<日期>_<hash>`）→ **分支会话登记在分支工作区的桶里，主桶从来没收到它**

**推论（协议的全部逻辑）**：Merge-Back 唯一的能力是**搬文件**。所以要让上下文跟着回来，就把上下文**做成文件**。

> ⚠️ **禁止**：手动搬 `desktop-sessions-v5\by-id\<hex>\` 或改 `topic-state-v1.sqlite`。Reasonix 会警告 `external modifications conflict with its saves and are preserved as conflict copies`，改动被降级为 `*.conflict.*.bak`，"改了像没改"，还可能损坏会话。

## 二、三件套

### ① CONTEXT.md 模板（放工作区根目录，文件名固定）

```markdown
# CONTEXT — <任务名>

> 维护者：分支会话 ｜ 每次合并前必须刷新
> 更新于：<YYYY-MM-DD HH:mm>

## 1. 任务目标
<一句话，含验收标准：怎样算做完>

## 2. 已确定的决策（主会话必须知道，不要重新讨论）
| # | 决策 | 理由 | 定于 |
|---|------|------|------|
| 1 |      |      |      |

## 3. 已完成
- [x] <条目>
- [ ] <未完成>

## 4. 产出物清单
| 路径 | 说明 |
|------|------|

## 5. 关键技术结论
<可验证的事实 / 命令 / 数据。禁止形容词，禁止"效果很好"这类无法证伪的描述>

## 6. 未决问题 / 卡点
- [ ] <问题 + 卡在哪 + 已试过什么>

## 7. 下一步（回到主会话后先做什么）
1. <可立即执行的动作>

## 8. 参考
<涉及的文件、外部链接、命令>
```

### ② 分叉时的开场白（粘进分支会话的第一条消息）

```text
本次任务在隔离工作区（会话分支）中进行，请遵守「上下文交接协议」：

1. 【开始前】检查工作区根目录的 CONTEXT.md。不存在就按协议模板创建；
   把主会话交代的背景写进第 1、2 节。
2. 【过程中】每产生一个新决策 / 新结论 / 新产出物，立即更新 CONTEXT.md 对应章节。
   不要攒到最后一次性写 —— 会漏。
3. 【每回合结束前】刷新「更新于」时间，并更新第 3、4、6、7 节。
4. 【目标】用户点「合并工作区分支」时，CONTEXT.md 是唯一能跨过隔离边界的载体。
   它必须让主会话读完即可无缝接续，不得依赖本会话的任何其它记忆。
```

### ③ 合并前的刷新指令

```text
合并前最后一件事：刷新 CONTEXT.md。
重点补全第 4 节「产出物清单」（确保每个文件都已写进工作区并能被 git 看到）、
第 6 节「未决问题」、第 7 节「下一步」。写完告诉我文件路径。
```

### ④ 合并后的读入协议（回到主会话说）

```text
读工作区根目录的 CONTEXT.md，按 1→8 节恢复上下文：
- 第 1、2 节：对齐目标与既定决策（已决项不再重新讨论）
- 第 4 节：核对产出物是否已随合并落到工作区（逐个确认存在）
- 第 6、7 节：确定下一步动作

读完先向我复述「目标 / 已决项 / 下一步」三项，等我确认无误再动手。
```

## 三、完整时序

```text
主会话                          分支会话                        git
  │                               │                             │
  ├── 分叉（隔离工作区）─────────▶│                             │
  ├── 粘「开场白」───────────────▶│                             │
  │                               ├── 建 CONTEXT.md ───────────▶│(工作区新文件)
  │                               ├── 干活 + 持续刷新 CONTEXT.md ▶│
  │                               │                             │
  │◀── 点「合并工作区分支」──────────────────────────────────────┤ merge worktreeBranch
  │        CONTEXT.md 随文件合并回主工作区 ──────────────────────┤
  │                               │(tab 关闭，会话仍在会话历史里)
  ├── 粘「读入协议」→ 复述三项 → 继续干活
```

## 四、反模式（每条都踩过或者已被证据否定）

- ❌ **攒到最后写** → 必然漏掉中途的决策分支
- ❌ **写成"聊天总结"** → 主会话读不出可执行项；必须是**字段化**的
- ❌ **堆形容词** → 「进展顺利」「效果不错」无法验证，等于没写
- ❌ **指望合并后主会话自动看到分支会话** → 已代码确证不可能
- ❌ **手动搬 session 文件** → 被 conflict 化，且可能损坏
- ❌ **用 CONTEXT.md 替代 git commit** → 它的职责是传递**意图与决策**，代码/文件本身照样要提交

## 五、边界（什么时候不需要这套协议）

- 任务只有一两轮、结论能当场说完 → 直接把结论贴回主会话即可
- 分叉只是为了跑一个独立任务、不需要主会话接续 → 不写 CONTEXT.md
- **真正需要**：任务跨多回合、产生多个决策、主会话必须接着往下做

## 六、相关

- 技能 `reasonix-workspace-mergeback-doctor` —— 合并被阻断（`active work` / 任务日志 / 未提交项）时的体检与修复
- `reasonix-autocommit.ps1`（每 2 分钟）会持续推进 master，所以合并面板常显示「落后 N」，**这是正常的**，不是冲突
