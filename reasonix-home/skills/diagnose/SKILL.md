# Diagnose — 诊断循环

## Phase 1 — 构建反馈环
**这是技能的核心。** 要有快速、确定性的复现手段。

构建方式（按优先级）：
1. 失败测试（单元/集成/e2e）
2. 对开发服务器的 curl/HTTP 脚本
3. CLI 调用 + 比较期望输出
4. 无头浏览器脚本（Playwright）
5. 回放抓取的真实请求
6. 一次性最小测试框架
7. 模糊测试（1000 随机输入）
8. git bisect 自动化
9. 差分对比（老版本 vs 新版本）

**在获得可靠的反馈环之前，不要进入 Phase 2。**

## Phase 2 — 复现
- [ ] 确认产生的失败模式与用户描述一致
- [ ] 多次运行可复现
- [ ] 记录了精确症状

## Phase 3 — 假设
生成 3-5 个排序假设，每个必须可证伪：
> 格式："如果 A 是原因，那么做 B 会让 bug 消失/更糟"

**向用户展示排序列表。** 他们常有领域知识快速重排。

## Phase 4 — 探针
每个探针对应 Phase 3 的特定假设。**一次只改变一个变量。**
- 优先：调试器/REPL
- 次选：带唯一前缀的定向日志 `[DEBUG-xxxx]`
- 性能问题：先测量再修复

## Phase 5 — 修复 + 回归测试
1. 先写回归测试 → 看它失败
2. 应用修复 → 看它通过
3. 重新运行 Phase 1 的反馈环验证

## Phase 6 — 清理
- [ ] 原始问题不再复现
- [ ] 回归测试通过
- [ ] 所有 `[DEBUG-*]` 日志已删除
- [ ] 一次性原型已清理
