## 结论：不改（2026-10-28 用户拍板）

用户问「能不能把 dsh 的进程级别提高一点？这个太低了吧」，实测后**决定不提**。

## 实测数据（i9-14900HX，32 逻辑核 = P-core 0-15 / E-core 16-31）

单线程 CPU-bound 基准，每格 5 次取中位：

| 配置 | 耗时 |
|---|---|
| Normal + 全核 | 206 ms |
| High + 全核 | 204 ms |
| Normal + P-core(0-15) | 205 ms |
| **Normal + E-core(16-31)** | **570 ms** |

- 优先级 Normal→High 差 **1%**（噪声内），因为 CPU 总占用只有 1.6-9.4%，32 核无竞争。
- 真正差 **2.8 倍**的是 P/E-core。但 Windows 调度器本来就把 dsh 放在 P-core（实测 CPU 0-15 忙度 40-64%，16-31 只有 4%）。
- 所有 dsh 进程的 EcoQoS 都是 off（`GetProcessInformation(ProcessPowerThrottling)` 查的），没有被系统降级。
- 电源计划「平衡」，但 AC 下 `PROCTHROTTLEMIN=100%`，已经满频。

## 判据（下次别再重复测）

**判断要不要提优先级，先看 `Get-Counter '\Processor(_Total)\% Processor Time'`**：单核占用 <50% 或总体 <20% 时，提优先级对单线程 JS 没有任何收益 —— 调度优先级只在**争抢**时起作用，空闲机器上它不改变任何东西。

真正该看的是「线程有没有被放到 E-core」，用逐核 `% Processor Time` 分布判断（忙的核在 0-15 就没事）。

## 不要做的事

- 不要为了让「任务管理器里看起来优先级高」而改 PriorityClass —— 那是观感，不是性能。
- 不要绑 affinity 到 P-core 当默认优化 —— 当前无收益，且会限制 libuv 线程池 / GC 线程的并行度。
