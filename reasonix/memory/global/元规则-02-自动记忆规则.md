# 规则：完成重要操作后自动 remember

**规则**：每次完成以下类型的操作后，必须自动调用 `remember` 保存结果，不等用户提醒。

**触发场景**：
- 安装/卸载软件 → 存版本、路径、配置方式
- 配置 API Key / 环境变量 → 存配置内容（不含 key 明文，存位置和方式）
- 批量文件操作（>5个文件）→ 存操作摘要
- 项目结构变更 → 存变更摘要
- 任何需要"下次还记得"的信息

**格式**：
- type: reference（工具类）或 project（项目类）
- description: 一句话说清存了什么
- content: 关键事实，让未来的我能直接引用，不用重新推导

**Why**：用户指出我经常丢失对话历史、不保存关键信息。这个规则解决"做完不存档"的问题。

## 追加：description 的检索冗余（2026-10-22 实测后加，硬约束）

**实测事实**（2026-10-22，398 条 insight / 294 条 fact 现场测）：
- `memory_search` 是**多词子串匹配**，不是语义检索。397/398 条 insight 都存了 3072 维 embedding，但**没有参与检索**（语义相近的查询照样 0 命中）。
- 单词、2–3 词查询工作良好：`bili` 20 条、`死锁` 3 条、`bili 压缩 死锁` 1 条精准命中当天新写的 fact。
- **4 词及以上的自然语言查询直接归零**：`bili 压缩 上下文窗口 死锁` → 0 条（而语料里有「压低窗口」「形成死锁」，只是缺「上下文窗口」这个四字连写）；`dsh 配置 热重载` → 只回 1 条不相关的。
- 纯子串匹配会串味：查 `bili` 命中一堆 `bilingual-*`（`bili` ⊂ `bilingual`）。

**因此每条 fact 的 `description` 必须铺检索关键词**，它和 `name` 是召回面的唯一杠杆：
1. 同一概念给三种写法：中文词 + 英文术语 + 用户的口语说法。例：`上下文窗口 context window 窗口 上下文长度`、`压缩 compact compress 折叠 fold`。
2. 名词不要只出现在正文里。正文里写「压低窗口」而不写「上下文窗口」，`上下文窗口` 这个查询就永远空手（上面实测就是这条踩的）。
3. 中英文各写一遍：`自动压缩 auto-compact 自动折叠`。用户常混着敲。
4. `name` 保持「主体-动作-日期」形状，把最重要的英文主体放在最前（`bili-window-150000-deadlock-根因与修复` 这种就能被 `bili`/`死锁`/`窗口` 三路召回）。
5. 别指望同义词自动扩展，也别为了命中堆无关词——子串匹配下堆词会把噪声一起拉进来。

**Why**：记忆系统的成本在写入，价值全在召回。description 写得省，等于把 fact 活埋。
