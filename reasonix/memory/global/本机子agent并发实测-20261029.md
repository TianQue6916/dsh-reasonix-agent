## 实测（2026-10-29，本机 i9-14900HX / 32 逻辑核，0-15 P-core / 16-31 E-core）

### CPU 密集并发 + 绑核效果

同一测量方式内对比（PowerShell `Start-Process` + `ProcessorAffinity`）：

| 配置 | 墙钟 | 结论 |
|---|---|---|
| 8 路 · 默认（全 32 线程） | **1150 ms** | — |
| 8 路 · 绑 P-core(0-15) | **878 ms** | **省 24%** |
| 16 路 · 默认 | 1401 ms | — |
| 16 路 · 绑 P-core(0-15) | 1259 ms | 省 10% |

另一组（bash 起进程，含 ~350ms 固定开销）：1 路 765 / 4 路 812 / 8 路 1034 / 16 路 1476 ms。
单进程基准 410ms；E-core 单线程 570ms vs P-core 205ms（**2.8 倍**）。

⇒ **绑 P-core 确有收益，8 路时最明显（-24%）**。16 路只能小赚，因为 P-core 只有 16 个逻辑线程（含超线程，非 2 倍性能）。

### subagent 并发（6 路只读任务）

**关键：本机只占 24.1%。**

```
6 个 subagent，16 次工具调用，本机执行时间合计 = 3056 ms
总墙钟 = 12700 ms  ⇒ 其余 75.9% 是 LLM API 往返 / 排队 / 首 token 延迟
```
那 3056ms 里还有很大一块是 bash 进程冷启动（270–330ms × N），不是计算。
⇒ **subagent 的瓶颈在 provider，不在 CPU。CPU 强 10 倍也只能把 12.7s 压到 ~3s。**

## 社区可用的手段（2026-10-29 检索）

### CPU 调度线（真有效）

| 手段 | 说明 |
|---|---|
| **Process Lasso** | 社区首推。绑 affinity 到 P-core、把后台赶去 E-core、持久规则。免费版即可绑核 |
| **异类线程调度策略** | 电源选项隐藏项（`PowerSettingsExplorer` 解锁），设「优先使用性能核心」；部分教程说把系统默认的 50 改成 100 |
| **E-core parking** | [Intel 社区实测](https://community.intel.com/t5/forums/forumtopicprintpage/board-id/processors/message-id/88682)：Core Ultra 9 275HX 上 **parking 全部 16 个 E-core 或取消勾选 Core 0，直接解除 40W 功率钳制** |
| `bcdedit /set numproc N` | 全局屏蔽部分逻辑核（激进，Windows 大版本更新会重置） |
| BIOS 关 E-core | 最激进，一劳永逸但损失缓存 |
| 代码里 `SetThreadAffinityMask` | 社区提醒**别写死**：核编号在别人机器上未必是 P-core |

### subagent / LLM 线（**都是排队限流，没有加速**）

- `dsh-concurrency-guard`（1.5.6）：挂 `llm/stream` 瀑布，统计全部在途请求，FIFO 排队，**带 WebUI 并发监控面板**
- `dsh-llm-concurrency`（myk5010）：process-wide per-provider 并发闸门
- `dsh-llm-rate-limit`（Asong6824）：per-provider RPM、token 预算、429 自适应冷却
- `dsh-tool-bulkhead`（@why-daydream）：per-tool / per-provider 隔离域，队列满拒绝
- `dsh-subagent-role-router`（643048695）：per-role 路由、多模型轮换、跨 provider failover、失败冷却 15s

**这些的价值是「避免 429 / 被封号」，不是把 12.7s 变成 3s。** 真实加速只能靠：减小每个 subagent 的上下文（省 prefill）、换更快的 route。
