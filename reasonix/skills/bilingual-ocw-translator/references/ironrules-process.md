## 流程类铁律

### 铁律 19：每一步都必须不断备份

**任何破坏性/合并性操作（波次落盘、合并、批量修复、覆盖输出）之前，必须先备份当前全部工作产物。** 备份频率以"每一步"为单位——多波次流水线中，宁可多备份，不可少备份。

**必做备份点（按流程顺序）**：
1. **开工前**：源 PDF、提取的原文文本、术语表 → 快照
2. **波 1 翻译 worker 落盘后**：立即打包 `pages/` 全部输出
3. **每次执行审计修改意见前**：备份当前合并稿
4. **合并前**：备份所有波次产物（`pages/`、`notes/`、`audit_report.md`）
5. **交付前**：备份最终稿

**备份规范**：
- 快照目录：`.reasonix/attachments/backup/<时间戳>-<阶段名>/`（如 `20260809-143000-merge-before/`），用 `cp -r` 或 `tar -czf` 打包含全部翻译工作产物
- **保留最近至少 3 份快照**，历史备份在交付确认前一律不删除
- 审计报告里附一份备份清单（时间戳 + 内容），确保每一步可回滚

**为什么**：多波次 + 多子代理 + 多轮审计修复，合并与批量修复是破坏性操作——一旦覆盖错误或合并失误，没有备份就必须整波重跑（每波 ≤32 子代理），成本极高。

### 铁律 20：一切审计 = 审计 + 修复一体（2026-09-07 用户拍板）

**所有审计环节（页级审计 / 超强审计 / 格式审计）一律「审计+修复一体」，禁止只列意见清单让主代理另派修复批**——两轮往返浪费一整轮派发 + 等待周期 + token。

- 审计 worker 通读后**直接输出修订后的完整文件/块**（🔴 结构性问题与 🟡 质量问题直接改好；🟢 细节顺手改）
- 每处实质修改可附一行简短说明（🔴 必须修复 → 🟡 建议修复 → 🟢 可选）
- **引文核验例外**：若需逐词回字幕核对（🎥 引文真伪/语境），审计方无字幕时不得自行判断引文去留——在该处标注「⚠ 待核：<存疑点>」由主代理统一核
- 主代理角色：回填修订版 + 处理「⚠ 待核」项 + 抽查 🔴 项修复质量，**不再整批另派修复**

### 铁律 21：Reasonix 不派任何子代理——一切子代理活全部转主力机 dsh（2026-09-07 拍板，2026-09-08 强化）

> 🚨 **用户原话（2026-09-08）："Reasonix 不需要子代理，需要子代理全部换成 dsh 任务，而不是 Reasonix 自己的。"** Reasonix 内建子代理**一律不用**——任何需要"另派一个代理干活"的场景（翻译 / 写注 / 审计 / 交叉引用 / 扩写 / 检索），**唯一执行通道 = 主力机 dsh**（`dsh-remote`，默认 flash；仅超强审计 `-pro`）。主代理只做：切分、组装 prompt、派发、回填结果、处理 ⚠待核项、格式收尾、机械自检。
>
> 🚨 **通道总表（2026-09-08）**：
> | 活 | 通道 |
> |----|------|
（终审环节）
> | 写注 / 翻译 / 页级审计 / 交叉引用 / 格式审计 | `dsh-remote`（默认 flash）或主代理 |
> | 小修复 / 格式调整 / 回填 | 主代理直改（铁律 22） |
> | Reasonix 内建子代理 | ❌ 不用 |
>
> 本技能内部提到的"子代理 / worker / v4.1 flash + thinking 子代理"等说法，均指 **dsh-remote 任务**（主代理把任务切成 ≤18KB 块后逐块派发），**不是** Reasonix 内建子代理。

### 铁律 22：dsh 用量纪律——全任务一档模型（v4.1 flash），难任务靠资料/prompt/多轮（2026-09-10 用户拍板）

> 🚨 **用户原话（2026-09-10）："v4.1 flash 全面超越 pro，以后就都用 v4.1 flash，需要 pro 的地方也换成 flash，不管什么任务都暂时用 flash，只不过难任务需要多查资料多给提示词多优化几轮。"** 全流程只有一档模型 `deepseek-v4.1-flash`；**pro 弃用**；难任务不做模型升级，而是**补充资料 + 加厚 prompt + 多跑几轮迭代**（`-e max` + 局部重跑）。
>
> **怎么应用**：
> 1. **一档模型制**：全流程统一 `dsh-remote -m deepseek-v4.1-flash`；`-e` 按难度选 off/low/high/max，没有 pro 档。
> 2. **小问题主代理直改**：修复注里的错字/粘连、补术语括号、调格式、回填错误等**局部机械小修**，一律主代理直改（或 `dsh-remote -m deepseek-v4.1-flash -e low "任务"`），不必动用大任务。
> 3. **判定"是不是难问题"**：决定的是 **effort 与迭代轮数**，不是模型——需深度推理/长文生成/多步证明 → `-e max` + 必要时多轮；机械替换/格式核对/单点修复 → 主代理直改。
> 4. **难任务的做法**：一批注整体扩写/重写 → `-e max` 一次成批；若只有个别注不合格，只对那几条**局部重跑**（`-e low/high` 小任务），不整批重跑。
> 5. 实战教训（part012 审阅 2026-09-08 + 2026-09-10 校准）：过去把 8 批全发 pro 审阅 → 每批 pro+max 跑 25-40 分钟、批次 7 跑偏；v4.1 flash 全面超越 pro 后，**同质量工作用 flash 跑更快更省**——质量靠 prompt 完整度与迭代轮数，不靠模型档位。

### 铁律 23：任何 dsh 任务必须先查小电脑 wiki 再回答/继续（2026-09-08 用户拍板）

> 🚨 **用户原话（2026-09-08）："派发任何子代理（dsh）都要求其能够先查小电脑 wiki 再回答和继续，强调 wiki 知识库的重要性。"** 每一条派发给 dsh 的任务，prompt 里**必须包含 wiki 先行指令**：先查小电脑知识库，再回答/继续干活。
>
> **小电脑（本机）知识库 = 派发给 dsh 时的必查资源**：
> 1. **PocketWiki**（8808，`tool-pocketwiki` / `http://localhost:8808`）——用户历史笔记、方舟资产、术语口径；本机常驻
> 2. **离线维基 ZIM**（51.9GB，`/media/OS/wiki-data/zim/wikipedia_en_all_nopic_2026-06.zim`，本机 openzim-mcp / libzim 直搜）——术语、历史人物、概念背景权威来源
> 3. **⚠️ 关键事实**：ZIM 与 PocketWiki **只有小电脑（本机）有**，主力机无——所以 dsh 任务本身无法直接查 wiki，**主代理必须在派发前把 wiki 检索结果注入 dsh prompt**（或派发后由主代理查 wiki 回填核对）
>
> **怎么应用**：
> - 派发任何 dsh 任务前，主代理先跑一轮 wiki 检索（关键词 → PocketWiki grep + ZIM 搜索），把命中的知识/术语/口径**作为上下文注入 dsh prompt**
> - dsh prompt 统一加一句：「如需查证术语/概念/史实，以下为本机知识库检索结果，请基于此回答」+ 注入内容；若注入不足，标注「⚠ 需主代理回查 wiki」
> - 写注 / 审计 / 翻译涉及术语、人名、年份、概念定义时，wiki 检索是**必做前置**（呼应铁律 13 全资源搜索）
> - 实战教训：模型对史实年份（如 Hausdorff 生年 1868 vs 1869）、概念归属易凭训练记忆出错——wiki 先行可拦截这类错误

### 铁律 24：扫描版（无文字层）源文件必须做视觉核对（2026-09-23 用户拍板「以后可以多侧重视觉」）

> 🚨 凡源文件是**扫描版**（`pdftotext` 提取为空、只能靠 OCR）的翻译任务，**交付前必须过references/vision-check.md的视觉核对流水线**：用 `deepseek/deepseek-v4.1-flash` 的**图像输入**逐页转写原书作为**权威原文** → 与译文比对 → 派终校任务以权威原文为准订正。
>
> **为什么必须**：Windows OCR 会**整段丢公式**。part004 实测三例——公式 (4) 在 OCR 里只剩一个 `and`（两式全丢）；$\delta<\sqrt{2}-1$ 被读成 `軛 一 1`，译者据上下文误还原为 `0.1`，还在注里围绕错误常数写了一整段；示例矩阵 $A_0,B_0,C_0$ 被写成 $A_{11},A_{12},A_{13}$。**这类错误任何基于 OCR 文本的审计都查不出来**，只有看原页才能发现。
>
> **配套必查**（详见 references/vision-check.md §9.4）：订正会**删注**（订正前后统计译者注条数，丢失的从备份回插）、```math 围栏失衡、任务超 **32767 字符**静默失败（rc=0 零输出）。
>
> **人机分工**：机器负责"看得全"（逐页转写 + 编号比对），人负责"看得懂"（相似度低的地方要人判断是不是等价改写）。

### 铁律 25：替换式改稿必须覆盖到公式边界 + 交付前必跑「公式体检」（2026-09-23 part005 实战）

**踩坑事实**：part005 视觉终校用「old 串只匹配到公式中途、new 串以 `（续）` 结尾」的补丁批量改 50 页，`$` 看似正常，但**7 处公式被撕成两半**：

- 3 处在正文行内 → 例：`从最后一个方程 $x_1 = \lambda x_4$ 出发…于是得到 $\lambda^4 = 1$。**mbda^4 q_1$**，于是…` → `$` 计数变奇数，可被捕获；
- 4 处在 ```math 围栏内 → 例：`... = \lambda_j u_j . \tag{3} **\text{ 1}}{h^2}** = \lambda_j(...)`、`\tag{4} **\text{ 2 \end{bmatrix} \tag{4}**`、`\tag{9}**tag{9}**`、`A for low frequencies, } D for high frequencies}` → **`$` 配对检查完全查不出来**；KaTeX 报错后 `throwOnError:false` 让公式以**裸 LaTeX 文本**出现在成品 PDF 里（`\frac`、`\begin{bmatrix}` 直接印在纸上），直到渲染完逐页看才发现 —— 白跑两轮渲染。

**三条纪律**：

1. **补丁的 old 串必须覆盖到公式/围栏的自然边界**（整行、整个 ```math 块，或至少到 `\tag{N}` / `\end{...}`）。宁可用更长、更唯一的 old 串，也不要「前半段匹配 + 后半段自动保留」。**严禁**在 new 串末尾留 `（续）`、`\text{`、`\tag{pre}` 这类「占位式接续」标记——它们就是撕裂源。
2. **交付前必跑公式体检**（主代理直跑，秒级；已并入 `check_mechanical_p005.py`）：
   - 围栏外逐行 `$` 计数必须为**偶**（忽略 `\$`）；
   - 围栏内逐行花括号 `{` / `}` 必须**相等**；
   - 围栏内不得出现 `\tag{X} \text{`、`\tag{X}tag`、同行两个 `\tag{`。
3. **改完合并稿必须同步改 `pages/` 源页**，否则下一次 `assemble` 会把回退带回来（part005 出现过这个次序陷阱：先改合并稿、忘了源页，第二次合并又裂开）。

### 铁律 26：原书插图是内容，不得静默丢弃（2026-09-23 用户拍板）

> 🚨 **凡原书有 Figure（插图 / 曲线图 / 示意图 / 谱图 / 流程框图 / 矩阵结构图），交付稿里必须留下这张图本身**——用 `assets/` 存图 + Markdown 引用；**只翻译图注文字 = 违规**。图注照双语铁律翻译；图内印字按 references/image-pipeline.md §10.2.5 决策树处理；难概念还**鼓励自行绘图**（references/image-pipeline.md §10.3），自绘图必须注明"译者绘制"。
>
> **暴露事实**：part005（Strang LaLFD 书页 198–248）交付稿里，**图 IV.1 只剩一行图注文字**（"$w$ 的各次幂也就是 $\omega$ 的各次幂……"），图本身（两个单位圆 + $N=8$ 标注 + $w=e^{2\pi i/8}$ 对照）从未进入交付物——读者拿不到原书里最直观的那张图。这类"丢图"在任何文本层审计里都不可见（没有文本可查），只有对着原页看才发现。
>
> **为什么**：图是构建主义读者理解空间/结构概念的第一通道；扫描版教材尤其危险——OCR 只吐文字，图在流水线里默认消失。
>
> **怎么做（三步，详见references/image-pipeline.md）**：① 视觉模型逐页定位插图并给**百分比 bbox**（§10.2.2，实测可用）；② PyMuPDF 高 dpi `clip` **重新渲染裁切**（references/image-pipeline.md §10.2.3，不要用屏幕截图、不要用 `pdfimages`——扫描版只会吐出整页 JPEG）；③ 存 `assets/` + 图注双语 + 交付前做"图数比对"（references/image-pipeline.md §10.5）。

> 💡 **根因**：这类撕裂源于「用替换串模拟续写」。真正安全的做法是**整块替换**（把要改的公式整段写进 old，整段写进 new），或**直接重写该行/该块**。
