# TDD — 测试驱动开发

## 核心原则
- 测试验证行为（Behavior）而非实现（Implementation）
- **好测试**：集成风格，通过公共接口测试，描述 WHAT 而非 HOW
- **坏测试**：mock 内部协作者，测试私有方法，打断内部重构

## 反模式：水平切片
**不要**先写所有测试再写所有实现。正确做法是**垂直切片**（Tracer Bullet）：

```
正确（垂直）：
  RED→GREEN: test1→impl1 → RED→GREEN: test2→impl2 → ...
```

## 工作流

### 1. 规划
- [ ] 确认用户需要的接口变更
- [ ] 确认要测试哪些行为（优先级排序）
- [ ] 设计可测试的接口
- [ ] 列出要测试的行为（非实现步骤）
- [ ] 获得用户批准

### 2. Tracer Bullet
写一个测试验证系统的一件具体事：
```
RED:   写第一个行为的测试 → 失败
GREEN: 写最少量代码通过 → 通过
```

### 3. 增量循环
对每个剩余行为重复 RED→GREEN，一次一个测试。

### 4. 重构
全部测试通过后，寻找重构点：消除重复、加深模块、SOLID 原则。

## 每轮检查清单
```
[ ] 测试描述行为而非实现
[ ] 测试只使用公共接口
[ ] 测试在内部重构后仍有效
[ ] 代码量正好通过当前测试
[ ] 没有预先添加未要求的特性
```
